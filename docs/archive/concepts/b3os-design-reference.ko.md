# b3os 설계 참고와 M4 상호운용성 방향

## 목적

Personal AgentOS M4는 사용자가 역할, 도구, 플러그인, 선택적 실행
런타임을 직접 소유·설정·승인·감사할 수 있게 하는 확장 계약을 만든다.
이 문서는 [b3rys/b3rys-team-os](https://github.com/b3rys/b3rys-team-os)의
공개 설계에서 얻은 운영 원칙과 AgentOS에 적용할 경계를 기록한다.

이것은 공개 참고와 감사 기록이다. b3os 유지관리자와 공동 개발, 제휴,
호환성 보장에 합의한 것은 아니며, 그러한 표현을 하지 않는다.

## 출처와 라이선스

- 프로젝트: `b3rys/b3rys-team-os`
- 검토 기준: `main`의 `fe4c3322b3bfcd0a9c52bdefa4789bc7b752737f`
- 확인일: 2026-09-07
- 라이선스: Apache-2.0

AgentOS는 이 단계에서 b3os 코드, 에셋, 또는 템플릿을 포함하지 않는다.
나중에 소스 또는 파생 저작물을 포함할 경우에만 Apache-2.0의 고지와
해당 NOTICE 의무를 배포물에 포함하고, 변경 범위를 명확히 기록한다.

## 채택할 설계 원칙

| b3os에서 참고한 원칙 | AgentOS M4 적용 |
| --- | --- |
| 역할과 책임을 명시적으로 등록 | agent manifest가 역할 정체성, 지시문, 허용 capability, 필요 연결, 지원 런타임을 선언한다. |
| 실행 런타임과 운영 책임 분리 | host API와 runtime adapter를 분리해 내장 모델과 선택적 외부 런타임이 같은 capability 계약을 사용한다. |
| 작업의 담당·검증·보고를 추적 | 실행 기록은 선택한 역할, 실제 도구, 승인 상태, 결과를 사용자가 확인할 수 있게 남긴다. |
| 외부 행동은 운영 통제 아래 둠 | 외부 쓰기·메시지 전송·셸·연결 폴더 밖 접근은 manifest 선언만으로 허용하지 않고 사용자 승인을 요구한다. |
| 팀 메시지는 신뢰할 수 없는 입력으로 취급 | 향후 agent 간 전달이 생겨도 외부/도구 결과는 지시가 아닌 검토 자료로 격리하고, 출처와 호출 체인을 기록한다. |
| 루프와 중복 실행을 방지 | 향후 협업 버스는 hop 제한, 멱등 키, 명시적인 완료 상태를 가져야 한다. |

## M4 계약의 경계

P4-01과 P4-02는 manifest·bounded host API·로컬 플러그인 수명주기의
기반을 이미 제공한다. 이 문서는 그 기반 위의 상호운용성 후속 작업을
기록한다.

- **Agent manifest**: 식별자, 표시 이름, 지시문, 허용 capability, 필요
  연결, 지원 runtime, 승인 요구사항을 versioned 형식으로 선언한다.
- **Tool/plugin manifest**: 제공 capability, 읽기/쓰기 영향, 필요 연결,
  설치·검증·비활성화·제거 수명주기를 선언한다.
- **Runtime adapter**: 실행기별 인증·호출 형식을 host API 뒤로 감추되,
  선언되지 않았거나 승인되지 않은 capability를 부여할 수 없다.

초기 계약은 단일 소유자, 연결된 폴더, 읽기 중심 capability, 명시적
승인, 재현 가능한 실행 기록을 유지한다.

## 이번 단계에서 하지 않는 일

- b3os 코드의 vendoring 또는 b3os 동작의 복제
- 팀 버스, 자동 담당 라우팅, 작업 카드, 에이전트 간 자동 전달
- 팀원별 Telegram/Slack 봇 또는 tmux 기반 상주 실행
- live Codex/Claude Code/OpenClaw 실행 어댑터
- 임의 셸, 외부 서비스 쓰기, 승인 없는 파일 쓰기

이 기능은 안전한 manifest·승인·감사 계약의 실제 실행 증거와 소유자의
명시적 우선순위 결정이 있은 뒤에만 별도 이터레이션에서 제안할 수 있다.

## 공개 소통과 향후 상호운용성

소유자가 구현 수준이 충분하다고 판단하고 외부 소통을 명시적으로
승인한 뒤 b3os 유지관리자에게 다음을 제안한다. 현재는 공개 이슈
초안을 게시하지 않는다.

1. AgentOS가 참고한 운영 원칙과 출처를 공유한다.
2. 양 프로젝트의 역할 정의·capability 메타데이터·runtime adapter에
   호환 가능한 공개 인터페이스가 있는지 논의한다.
3. 합의가 생긴 경우에만 공동 이슈 또는 PR 링크를 양쪽 문서에 추가한다.

응답 또는 합의 전에는 이 프로젝트를 b3os의 파트너나 공동 개발로
표현하지 않는다.
