# Assistant Execution — removed lookup-hardening history

Extracted by DOCS-CONSOLIDATE-04 (#1057) from the canonical [Assistant Execution Contract](../../../assistant-execution-contract.en.md). These clauses are explicitly marked removed by SEC-PILOT-01 #654 / the Secretary pilot posture. They are preserved for future hardening/threat-model reference, not as current request-path policy.

  - **(Removed by #654.)** judges the lookup when it includes **any** content of the owner's current message. This is decided inclusively: every outbound word counts unless it is taken from an *earlier* permitted text and not from the current message, so a reformatted, split, spelled-out or translated value counts. The current message and the **whole** outbound term list (capped at 12 terms; terms beyond the cap are never sent) go once to the existing DecisionEngine judgment path (`ConversationJudgments.lookup_term_sensitivity`, the #597 seam, via the `choose_many` typed envelope over index labels: the one owner utterance and the term list, the same route and audit; qualification suite `decision-qualification/2` probes it). The engine returns the terms to withhold; a confident empty answer (release everything) must meet the binary threshold (0.75). Withheld terms stay withheld for the rest of the Work, before any later judgment, so a reordered or re-added value cannot resample it. The result is cached per (current message, term *set*), and at most 6 judgments are asked per Work. The explicit-`/search` use, the judgment count and the withheld set are durable per Work across processes (the CLI host preflight, the bridge, a restarted bridge): one `work_lookup_state:<work>` config row per Work, updated in one immediate transaction. Withheld values are stored only as one set of truncated keyed digests per Work (HMAC with a local store secret) of each value's normalised form, its 2–8-character spans, its 5–8-jamo spans and every 4-digit window of its digit runs, over the **whole** value; at most 72 withheld values (`LOOKUP_DIGEST_ENTRIES`, six judgments of twelve terms) and 4096 digests (`LOOKUP_DIGEST_TOTAL`) per Work — past either the row is marked overflowing and nothing more is admissible. No text and no lengths are stored. Only rows of Works that no longer exist or can never run again under the same id (`succeeded`, `cancelled`, `partial`, `unknown`, `interrupted`; `LOOKUP_STATE_TERMINAL`) are pruned: a parked (`awaiting_*`) or failed Work can be re-queued under its id and keeps its state. At most 1000 state rows are kept (`LOOKUP_STATE_ROWS_MAX`); past it a new Work cannot record state and its lookups are refused with a truthful reason rather than run without state (fail closed; failed Works are kept because deleting their rows could let a re-queued Work start with a fresh withheld set). If recording a withheld value fails, the value stays withheld in the process, the row is marked overflowing when possible, and the lookup is refused — never a silent loss. Without the store secret nothing is persisted and the state stays in the process; a corrupt row fails closed (no claim, nothing admissible). With no engine (including Jev, route off, a subscription-CLI decision route inside the bridge), an unavailable, abstaining, malformed or contradictory answer, or the per-Work cap reached, **no current-message content is sent**; words taken from earlier permitted text may still go out. The worker then receives AgentOS's truthful reason (the judgment is not configured or not available — pointing to Settings › 대화 해석 —, the selected decision route cannot make this judgment (Jev), not certain, the per-Work cap, or unavailable on the CLI bridge), never an instruction to retype the request. No new model, cue list or regex decides sensitivity;

  - **explicit `/search <query>` (owner decision D1; since #654 a convenience, not a requirement: the once-per-Work claim, the judgment bypass and the withheld-value exclusion below are removed).** When the owner's current message is `/search <query>` and the worker proposes exactly that query (whitespace-normalised), that typed string is sent for that one lookup without the sensitivity judgment, minus saved private values **and minus values the judgment withheld earlier in this Work** (owner scope clarification), in every variant above. Worker-rewritten or added words are not covered and go through the normal composition. This applies on the direct-API route and to the CLI route's host-side preflight; the typed string is capped at the provider's 500 characters (`LOOKUP_EXPLICIT_QUERY_MAX`);

  - **(Removed by #654: a private context sends the worker's query exactly as a clean one does, minus excluded values; no owner-worded selection, dedupe, order, 8-word cap or one attempt per destination.)** when the context holds private material, keeps only words taken from text permitted for this lookup (`lookup_sources`): earlier owner messages whose Work read or wrote no private store (a durable successful write event labels its Work with the store's label, whichever process ran it), earlier replies whose Work saw only owner conversation, and the owner's current request. A word must equal a permitted word or be a prefix of one; a word that extends a permitted word sends only the permitted word, so `병원이혼` sends `병원`. Digit runs must be identical. Words are deduplicated, put in the order they have in permitted text (message by message; the worker's order is not kept) and capped at 8. One network attempt per destination per Work is claimed as a durable `requested` tool event in one immediate transaction *before* the request, so a repeat, a second or restarted bridge process or a resumed Work gets no second attempt.

  - *Covert encoding by a hostile worker (accepted residual, owner threat scope 2026-09-26).* In a clean context the worker writes its own query words. A worker that deliberately encodes information in which characters and words it writes, their order and the allowlisted punctuation cannot be stopped while worker-authored queries are allowed; AgentOS guarantees deterministically only that no saved or withheld value leaves in any format or split variant. The channel is bounded, not closed, and every number here is enforced in code: at most 120 characters per clean-context query (`LOOKUP_CLEAN_QUERY_MAX`; words of at most 24 characters, `LOOKUP_CLEAN_WORD_MAX`; at most 12 distinct words, `LOOKUP_CLEAN_WORD_CAP`; at most 12 operator characters, `LOOKUP_SEPARATOR_TOTAL`). A character can be any letter or digit of any script, about 150,000 assigned code points, so at most about 17.2 bits per character: at most about 2.1 kbit per lookup (120 × 17.2), and at most 6 clean-context lookups per Work (`LOOKUP_CLEAN_PER_WORK`), at most about 12.4 kbit per Work. A clean-context weather lookup carries at most a 120-character place plus an ISO 3166-1 alpha-2 code (8 bits) within the same 6 lookups. This applies only to a deliberately hostile worker; it is not a format-variant leak. **(Bounds removed by #654 except the provider's 500-character query limit; the residual is accepted under the pilot posture.)**

  - *Selection channel (removed by #654 with the private-context selection).* From a private context the worker still chooses which permitted words to keep. Dedupe, AgentOS ordering, the 8-word cap and one attempt per destination bound it; they do not remove it (at most one subset of at most 8 permitted words per destination per Work).

  - *Sensitivity judgment scope (accepted by the owner; removed by #654).* Only the current message is judged. A sensitive word of an *earlier* owner message whose Work wrote no private store remains permitted text.

  - *Judgment route (removed by #654: the bridge sends the lookup with no judgment on every decision route).* The Jev route offers no multi-selection and answers unavailable, which withholds current-message content. On the CLI route, lookups the CLI makes through the MCP bridge get **no** judgment when the owner's decision route is a subscription CLI: that CLI cannot run inside the CLI's restricted bridge environment, so the bridge fails closed with the truthful reason instead of attempting it. A host round trip is the not-activated follow-up [#629](https://github.com/Jongtae/agentos/issues/629). The host-side `/search` preflight is unaffected. With a direct-API decision route the bridge builds an `AgentService` over the same store; decision-audit appends are one immediate transaction, safe across the two processes.

  - *Private-context place names (owner wording no longer required since #654).* Owner-worded Korean place names may not geocode: the #622 review reported that Open-Meteo (`language=en`) resolved `대전` to a place in KP and found nothing for `서울`, `광주` or `제주` (not observed by the tests here). Such a lookup then fails or answers for the wrong place.

  - *Ordering.* A lookup in an earlier model step than a private-store write of the same Work is not retroactively covered by the exclusion; the current-message judgment covers the value when it is in the current message. (The current-message judgment is removed by #654: an unsaved value the owner typed is sent.)

  - *Rollback (removed by #654).* In restrictive mode a clean context is still composed (judgment and place wording); a private context is refused.

- **Rollback (removed by #654: `egress_composition` is no longer read).** `egress_composition = {"mode": "restrictive"}` refuses a lookup from a private context instead of composing it, and treats every shown earlier message as history-tainted. That is stricter than either route before #605.
