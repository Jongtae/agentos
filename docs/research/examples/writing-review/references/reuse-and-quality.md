# Practical reuse and quality review

Use the original author's purpose, not originality, as the success criterion.

For every substantive design proposal, answer: What requirement matters? Which internal concept or code already addresses it? Which public concept, structure or implementation is comparable? What is directly reused, what is adapted and what is not proven? What concrete gap would justify new code?

Prefer primary sources. Keep source title, exact URL, inspected section/version, date and evidence level. Label project adaptations explicitly. Do not treat a search excerpt as full review, a reference format as compatibility, or a professional standard as the software's legal qualification.

Current-code checks and historical design documents can disagree because the implementation progressed. Record the inspected commit and symbols; do not silently declare every older gap still open.

Check normal and counterexamples: request vs accepted responsibility; analysis vs action; submission vs completion; totals vs available amounts; same-name vs same entity; unknown vs failure; restarted work vs duplicate external effect; same-model personas vs independent evidence.

For reuse of code, do not skip pinned revision, licence, maintenance, dependencies, platform fit, security and small compatibility tests. Content-only adaptation does not itself select a runtime dependency.

Final editor: thesis, progression, terminology, non-repetition, readable artifact and practical takeaways. Final auditor: no material unresolved defect, source support, evidence boundaries, authority, counterexamples, same-bundle verdicts and substantive reuse comparison. Use PASS / REVISE / BLOCKED with reasons, not invented numeric confidence scores.
