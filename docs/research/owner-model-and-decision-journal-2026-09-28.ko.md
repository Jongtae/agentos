# 믿음과 판단을 SQLite 원장에 직접 새기기

Personal AgentOS의 owner model과 decision journal로 그대로 가져다 쓸 수 있는 오픈소스 라이브러리는 **없다**. 대신 검증된 아이디어를 조합해 AgentOS 자체 SQLite 스키마로 **Build**하는 것이 맞다. 조합할 재료는 다음과 같다. 믿음(belief) 쪽은 Zep/Graphiti의 bitemporal fact 모델("invalidate, don't delete"), W3C PROV의 출처 어휘, Generative Agents의 evidence 링크, Mem0의 history 테이블, Letta의 라벨·크기 제한 memory block을 쓴다. 판단 쪽은 OpenTelemetry GenAI semantic conventions와 MLflow의 Assessment 레코드 형태를 쓴다. 후보 시스템의 라이선스는 거의 모두 Apache-2.0 또는 MIT라서 AGPL-3.0 제품에 문제가 되지 않는다. 걸림돌은 저장소다. Mem0는 Qdrant 같은 벡터 스토어, Graphiti는 Neo4j/FalkorDB, Langfuse는 Postgres+ClickHouse를 요구하므로, 채택하면 정본(canonical) 소유자 상태가 AgentOS 밖으로 나간다. 판단 기록 쪽의 핵심 근거는 연구 결과다. CoT는 실제 추론을 충실히 드러내지 않으며, 힌트를 사용한 경우에도 이를 언급하는 비율이 흔히 **20% 미만**이다([Chen et al.](https://arxiv.org/abs/2505.05410)). 따라서 감사 기록은 숨은 사고 과정이 아니라 관찰된 결정 라벨, 입력 digest, 사용한 evidence 참조, 실제 도구 결과를 남겨야 한다. 사용자 연구도 같은 방향이다. ChatGPT 메모리의 **96%가 시스템이 일방적으로 생성**한 것이고([Dash et al., WWW '26](https://arxiv.org/abs/2602.01450)), 주요 상용 제품 중 어느 것도 기억 항목에서 원본 대화로 돌아가는 출처 링크나 연쇄 삭제를 제공하지 않는다. 그러므로 **믿음마다 출처가 붙고, 삭제가 파생물까지 전파되며, 삭제 영수증이 남는 로컬 원장**이 AgentOS가 차별화할 수 있는 지점이다. 이 방향은 C16과도 맞는다. 사실 추출, 모순 판단, 목표 달성 평가는 소유자가 선택한 AI가 하고, AgentOS 코드는 검증, 저장, 시간 경계, 출처, 삭제만 맡는다.

## 메모리 시스템 아홉 개 중 정본이 될 수 있는 것은 없다

agent memory 분야는 이미 성숙했지만 대부분 서버형 벡터·그래프 DB를 전제로 한다. 개념의 뼈대는 **CoALA**가 제공한다. CoALA는 working/episodic/semantic/procedural memory를 나누고, 결정 주기를 propose → evaluate → select → execute로 정리했다([Sumers et al.](https://arxiv.org/abs/2309.02427)). 이 어휘로 보면 AgentOS에는 두 가지가 필요하다. owner model은 semantic과 episodic memory에 해당하고, decision journal은 그 결정 주기를 기록하는 장치다.

**MemGPT/Letta**는 context 안에 항상 머무는 "core memory block"이라는 개념을 만들었다. block에는 `label`, `description`, `value`, `limit`(문자 수 상한), `read_only` 필드가 있다([Letta docs](https://docs.letta.com/guides/agents/memory-blocks)). 그러나 임베드 가능한 Python 서버(V1)는 `archive` 브랜치로 은퇴했다([letta-ai/letta](https://github.com/letta-ai/letta)). PyPI `letta` 0.33.4는 이제 Node.js를 번들한 TypeScript CLI이며, 패키지 설명에 스스로 "not a Python SDK or API server"라고 적혀 있다([PyPI letta](https://pypi.org/project/letta/)). 후속 제품인 Letta Code는 모든 context를 git으로 추적하는 MemFS와 sleep-time "dreaming" 기능을 갖췄지만, 기본 백엔드는 Letta Cloud다([letta-code](https://github.com/letta-ai/letta-code)). 가져올 것은 아이디어다. 적은 수의 라벨 붙은 block, 소유자 동의 없이는 바꿀 수 없는 `read_only` 플래그, block별 버전 이력이 그것이다. 반면 block에는 사실 단위의 출처, 신뢰도, 유효기간이 없다. block 스키마에 있는 귀속 정보는 `last_updated_by_id` 수준이 전부다([block.py](https://github.com/letta-ai/letta/blob/archive/letta/schemas/block.py)).

**Generative Agents**(Park et al.)는 memory stream을 append-only 로그로 설계했다. 각 항목은 자연어 설명, 생성 시각, 마지막 접근 시각을 가진다. 검색 점수는 recency(0.995 지수 감쇠), LLM이 매긴 importance(1–10), embedding relevance의 합이다. 최근 사건의 importance 합이 **150을 넘으면 reflection**을 만들고, 각 reflection은 근거가 된 기억을 가리킨다. ablation에서 믿음직함(believability) 점수는 전체 29.89, reflection 제거 시 26.88, 메모리 제거 시 21.21이었다([ar5iv 2304.03442](https://ar5iv.labs.arxiv.org/html/2304.03442)). 이 설계에서 가져올 것은 두 가지다. 하나는 파생 믿음이 evidence ID를 품어 "왜 그렇게 생각하나"에 답할 수 있게 하는 구조다. 다른 하나는 importance 누적을 트리거로 쓰는 배경 통합 방식인데, 턴마다 모델을 호출하지 않으므로 저장소의 verification budget에 맞는다. 다만 recency 감쇠는 검색 순위 신호로만 써야 한다. 알레르기처럼 한 번 말한 뒤 다시 묻지 않는 사실이 감쇠 때문에 삭제되어서는 안 된다. 코드는 2024-08 이후 동결됐다([GitHub](https://github.com/joonspk-research/generative_agents)).

**Mem0**는 논문과 현재 OSS가 서로 다르다. 논문은 LLM이 새 사실을 top-10 유사 기억과 비교해 ADD/UPDATE/DELETE/NOOP 중 하나를 고르는 파이프라인을 제시했다. 그래프 변형인 Mem0g는 모순된 edge를 삭제하지 않고 invalid로 표시한다([arXiv 2504.19413](https://arxiv.org/html/2504.19413)). 2026년 OSS는 추가만 하는(additive) 추출로 바뀌었고([PR #4805](https://github.com/mem0ai/mem0/pull/4805)), 그래프 메모리는 "Mem0 Platform feature"로 OSS에서 **제거**됐다([PR #6808](https://github.com/mem0ai/mem0/pull/6808)). 쓸 만한 부분은 SQLite `history` 테이블이다. 컬럼은 `id, memory_id, old_memory, new_memory, event, created_at, updated_at, is_deleted, actor_id, role`이다([storage.py](https://github.com/mem0ai/mem0/blob/main/mem0/memory/storage.py)). 또 하나는 기억 UUID를 정수로 바꿔 LLM의 ID 환각을 막는 기법이다([main.py](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py)). 라이선스는 Apache-2.0이고 2.2.1이 2026-09-25에 나올 만큼 활발하다. 하지만 벡터 스토어 어댑터 약 28개 가운데 SQLite가 없다([vector_stores](https://github.com/mem0ai/mem0/tree/main/mem0/vector_stores)). 벤더 논문 사이의 수치 충돌도 짚어 둔다. Mem0 논문은 Zep이 대화당 600K 토큰 이상을 쓴다고 주장한다. Zep 논문은 LongMemEval(gpt-4o)에서 71.2%로 full-context의 60.2%를 앞선다고 주장한다([arXiv 2501.13956](https://arxiv.org/html/2501.13956)). 둘 다 상대를 불리하게 측정한 벤더 수치이므로 선택 근거로 쓰기 어렵다.

**Graphiti/Zep**은 이 조사에서 시간 유효성과 대체(supersession)를 가장 완성도 있게 구현한 OSS다. 원본 입력을 손실 없이 episode로 보존하고, 모든 fact edge가 episode로 역추적된다. 각 edge는 네 개의 시각을 가진다. 사건 시간축의 `t_valid`/`t_invalid`와 수집 시간축의 `t′_created`/`t′_expired`다. 모순이 생기면 기존 edge의 `t_invalid`를 새 edge의 `t_valid`로 닫는다([arXiv 2501.13956](https://arxiv.org/html/2501.13956)). Apache-2.0이고 약 31K star, v0.30.2로 매우 활발하다. 그러나 백엔드는 Neo4j, FalkorDB(Lite), Neptune뿐이고 Kuzu는 deprecated이며 **SQLite 드라이버는 없다**([graphiti_core/driver](https://github.com/getzep/graphiti/tree/main/graphiti_core/driver)). 스키마 아이디어는 가져오되 의존성으로 채택하지 않는다. 쓰더라도 재구축 가능한 파생 인덱스로만 둘 수 있다. FalkorDB Lite의 라이선스는 이번 조사에서 확인하지 못했다.

나머지 후보는 한 가지씩 빌릴 아이디어를 준다. **LangMem**은 "profile"과 "collection"을 구분한다. profile은 스키마가 고정된 단일 문서라 갱신이 곧 교체다. collection은 여러 레코드라 조정(reconciliation)이 필요하다. 메모리 쓰기도 hot path와 background로 나눈다([LangMem guide](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)). 다만 MIT에 0.0.30(2025-10)에 머물러 있고 LangGraph `BaseStore`에 묶여 있다. **A-MEM**의 "memory evolution"은 이웃 노트를 조용히 다시 쓴다([arXiv 2502.12110](https://arxiv.org/html/2502.12110)). 검사 가능해야 하는 owner model에서는 이것을 새 버전 생성으로 바꿔야 한다. **MemOS local plugin**은 "local SQLite"에서 FTS5와 벡터를 섞은 hybrid search와 Memory Viewer를 제공한다. 1인용 하이브리드 메모리가 SQLite만으로 충분하다는 아키텍처 증거가 되지만, 배포 형태가 npm 플러그인이다([MemTensor/MemOS](https://github.com/MemTensor/MemOS)). **LongMemEval**은 500문항으로 knowledge update, temporal reasoning, abstention을 따로 측정한다. 상용 비서와 long-context LLM이 긴 상호작용에서 약 **30% 정확도 하락**을 보인다고 보고했다([arXiv 2410.10813](https://arxiv.org/abs/2410.10813)). 이 세 범주는 AgentOS owner model의 수용 테스트로 그대로 옮길 수 있다.

## 믿음의 네 시각과 PROV 어휘가 "왜 그렇게 믿었나"에 답한다

owner model이 "X를 믿는다"에서 한 단계 나아가 "지난 화요일에는 무엇을 왜 믿었나"에 답하려면 데이터 모델링 표준이 필요하다. 여기서는 오래된 표준들이 최신 agent memory 라이브러리보다 쓸모가 크다.

첫째는 **bitemporal 모델**이다. SQL:2011은 application-time period(유효 시간)와 system-versioned(트랜잭션 시간) 테이블을 정의한다([Wikipedia: Temporal database](https://en.wikipedia.org/wiki/Temporal_database)). 전통적인 관계형 구현은 valid-from/valid-to/system-from/system-to 네 컬럼을 추가하는 것이다([XTDB](https://xtdb.com/blog/building-a-bitemp-index-2-resolution)). SQLite는 이를 네이티브로 지원하지 않으므로 컬럼과 트리거로 구현해야 한다([ohnekontur](https://www.ohnekontur.de/2024/02/19/unlocking-time-harnessing-the-power-of-temporal-tables-in-sqlite/)). 여기서 중요한 구분이 하나 있다. Graphiti는 두 종류의 변화를 모두 `t_invalid` 하나로 처리하지만 AgentOS는 이를 분리해야 한다. 하나는 "그때는 참이었고 지금은 아니다"(이사, 끝난 회의)로, 유효 시간 `valid_to`만 닫는다. 다른 하나는 "우리가 틀렸다"(오추론, 소유자 정정)로, 트랜잭션 시간 `retracted_at`과 사유를 기록한다. **Wikidata**의 rank 체계가 정확히 이 구분을 쓴다. 역사적으로 맞는 값에는 `start time`/`end time` qualifier를 붙이고, 오류로 판명된 값은 *deprecated* rank와 "reason for deprecated rank"(P2241)로 표시하며 지우지 않는다. 지우지 않기 때문에 같은 오류가 다시 추가되는 것을 막을 수 있다([Wikidata Help:Ranking](https://www.wikidata.org/wiki/Help:Ranking)).

둘째는 **W3C PROV**다(Recommendation, 2013). Entity/Activity/Agent 세 유형과 `wasGeneratedBy`, `used`, `wasDerivedFrom`, `wasAttributedTo`, `wasInvalidatedBy` 관계, 그리고 파생의 하위 유형인 Revision, Quotation, PrimarySource를 제공한다([PROV-DM](https://www.w3.org/TR/prov-dm/)). PROV-O의 `hadPrimarySource`는 "주제에 대해 직접 경험과 지식을 가진 agent가 만든" 출처를 뜻하므로([PROV-O](https://www.w3.org/TR/prov-o/)), "소유자가 직접 말했다"와 "모델이 추론했다"를 가르는 표준 어휘가 된다. 대응 관계는 다음과 같다. 믿음 행은 Entity다. Work, 대화 턴, 관찰 수집, 소유자 정정은 Activity다. 소유자, decision model, worker AI는 Agent다. Python `prov` 패키지는 MIT이고 v3.2.2(2026-09-18)로 건강하지만 저장 계층이 없는 메모리 내 직렬화기다([PyPI prov](https://pypi.org/project/prov/)). 그러므로 PROV의 어휘는 SQLite 컬럼과 edge 유형 이름으로 Adopt하고, `prov` 패키지는 "내 출처를 PROV-JSON으로 내보내기"용 선택적 export adapter로만 둔다. 구버전은 `lxml`, `rdflib` 등을 끌어왔으므로 현재 의존성 목록은 채택 전에 확인해야 한다.

셋째는 **신뢰도와 가설**이다. 이 조사에서 개인 agent의 믿음에 보정된(calibrated) 신뢰도를 정의한 표준이나 OSS는 찾지 못했다. Generative Agents의 importance는 신뢰도가 아니고, Graphiti는 신뢰도 점수 대신 최신 정보 우선으로 충돌을 해결한다([arXiv 2501.13956](https://arxiv.org/html/2501.13956v1)). 대신 W3C VC Data Model 2.0이 `validFrom`/`validUntil`/`evidence`/`credentialStatus`라는 표준 이름을 제공한다([VC 2.0](https://www.w3.org/TR/vc-data-model-2.0/)). 실용적인 조합은 네 가지를 함께 저장하는 것이다. `kind`(stated/observed/inferred/hypothesis), 모델이 보고한 `confidence`(보정되지 않은 참고값), `prov_edges`를 통한 evidence, 그리고 휘발성 유형에 필수인 `expires_at`이다. 이 입력들로 "지금 쓸 수 있는 사실인가"를 판단하는 일은 decision model에 맡긴다. 범주별 임계값을 코드에 하드코딩하면 C16 위반이 된다.

AgentOS 저장소는 이미 이 방향으로 반쯤 와 있다. `memories` 테이블에는 `supersedes`와 `state`가 있지만 유효 시간과 `retracted_at`이 없다([quickstart_store.py](../src/personal_agent/quickstart_store.py)). `context_observations`에는 `observed_at`/`received_at`/`valid_until`/`expires_at`/`state`가 있고 `current_state_claims`에는 `effective_from`/`effective_until`이 있어, bitemporal 구조에 가깝다([context_observations.py](../src/personal_agent/context_observations.py)). `memory_candidates`와 `memory_approvals`도 이미 있다. 따라서 새 프레임워크를 도입할 이유가 없고, 기존 테이블을 확장하는 Adapt가 정답이다.

## 잊기는 행 삭제가 아니라 파생물 추적, 물리적 소거, 영수증까지 포함한다

상용 비서들은 삭제 의미론에서 모두 약점을 보인다. Claude는 대화를 지워도 거기서 생성된 memory 항목은 남는다고 명시한다([Claude Help Center](https://support.claude.com/en/articles/11817273-how-does-claude-s-memory-work)). ChatGPT도 채팅을 지우는 것만으로 saved memory가 지워지지 않는다([OpenAI Help](https://help.openai.com/en/articles/11146739-how-does-reference-saved-memories-work)). Microsoft Copilot은 삭제에 두 단계가 필요하고, 30일 안에 다시 켜면 삭제된 기억이 **복원된다**([Microsoft Support](https://support.microsoft.com/en-us/microsoft-365-copilot/personalize-what-microsoft-365-copilot-remembers)). 규제 현장도 비슷하다. EDPB의 2025 공동 집행(32개 DPA, 764개 controller) 결과, 백업에서 지우지 못하는 기술적 한계와 문서화된 삭제 절차의 부재가 반복적인 실패로 지적됐다([EDPB report](https://www.edpb.europa.eu/system/files/2026-02/edpb_cef-report_2025_right-to-erasure_en.pdf)). ICO는 백업을 즉시 덮어쓸 수 없다면 "beyond use" 상태로 두라고 요구한다([ICO](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/individual-rights/right-to-erasure/)).

SQLite에서 물리적 소거에는 함정이 세 개 있다. 첫째, `PRAGMA secure_delete`는 기본값이 꺼져 있고, 켜더라도 FTS3/FTS5 shadow table에는 흔적이 남을 수 있다([SQLite PRAGMA](https://www.sqlite.org/pragma.html)). 둘째, FTS5에는 **SQLite 3.42.0**부터 별도의 `secure-delete` 옵션이 있으며, 이를 켜면 파일 포맷이 바뀐다([FTS5 docs](https://www.sqlite.org/fts5.html)). 셋째, WAL 모드에서는 checkpoint 이후에도 WAL 파일이 truncate될 때까지 옛 내용이 남는다([antonz](https://antonz.org/sqlite-secure-delete/)). 포렌식 도구는 freelist와 WAL 프레임에서 삭제된 레코드를 복구한다([bring2lite](https://www.sciencedirect.com/science/article/pii/S1742287619301677)). APFS 스냅샷, Time Machine, SSD wear-levelling이 페이지를 보존하는 정도는 확인된 자료가 없다. 따라서 파일 수준 소거는 best-effort라고 정직하게 표시해야 한다.

추가 암호 라이브러리 없이 구현할 수 있는 해법은 Verraes의 **Forgettable Payloads**다. 개인 내용은 별도 payload 테이블에 두고, 로그는 payload ID만 참조한다([Verraes](https://verraes.net/2019/05/eventsourcing-patterns-throw-away-the-key/)). crypto-shredding(항목별 키를 폐기하는 방식)은 append-only 로그와 백업에 유용하다. 다만 Python stdlib에는 AEAD 암호가 없어 `cryptography` 의존성이나 Keychain이 필요하고, 복호화된 값을 저장한 파생물까지는 막지 못한다. 그래서 C15 검토 항목으로 남긴다. 잊기 트랜잭션은 다음 순서로 진행한다. 먼저 `WITH RECURSIVE`로 `prov_edges`의 파생 closure와 supersession chain을 모두 구한다. 이어서 `secure_delete=ON` 상태에서 내용 행, FTS 행, 임베딩 행을 지우고 Evidence 안의 인용문을 비운다. 그다음 내용 없는 **erasure receipt**를 append-only 로그에 남기고, 마지막으로 `wal_checkpoint(TRUNCATE)`를 실행한다. 영수증에는 범위, 테이블별 건수, 방법, 그리고 이미 내용을 받은 외부 수신자(worker AI, 모델 API 등)를 기록한다. 도시 이름처럼 짧은 사실은 무차별 대입으로 역산될 수 있으므로 평문 `sha256(content)`를 넣지 않는다. 외부로 이미 나간 사본은 AgentOS가 회수할 수 없으므로 영수증은 원격 삭제를 주장하지 않는다(C6).

변조 탐지에는 stdlib `hashlib`로 만든 hash chain이면 충분하다. RFC 9162 Merkle tree와 signed tree head는 여러 당사자가 운영자를 믿지 않는 상황을 위한 설계다([RFC 9162](https://www.rfc-editor.org/rfc/rfc9162.html)). Trillian은 maintenance mode로 들어가 Go 라이브러리인 Tessera로 넘어갔으므로([google/trillian](https://github.com/google/trillian)) 이 제품 규모에는 과하다. "Agent Flight Recorder"는 hash chain, Merkle batching, 외부 anchoring을 조합해 이벤트당 중앙값 약 48 µs의 오버헤드와 편집·삭제·재정렬·fork 탐지율 100%를 보고했다([arXiv 2609.01931](https://arxiv.org/abs/2609.01931)). 이 수치는 2026-09에 나온 저자 자체 보고이며 아직 재현되지 않았다. 한계도 분명하다. SQLite 파일을 다시 쓸 수 있는 사람은 체인도 다시 계산할 수 있으므로, 로컬 체인만으로는 버그나 실수에 의한 변조만 드러난다. 공격자에 대한 증거력이 필요하면 체인 head를 소유자의 휴대폰이나 git처럼 외부에 주기적으로 anchor해야 한다. 체인에는 내용 없는 이벤트만 넣어야 잊기와 충돌하지 않는다. 그래야 erasure receipt 자체가 "여기서 무언가 삭제됐다"를 증명하는 체인 이벤트가 된다.

## 판단 기록은 CoT 대신 라벨, digest, evidence 참조, 관찰된 결과로 남긴다

decision journal에서 가장 먼저 정할 원칙은 숨은 사고 과정을 저장하지 않는 것이다. Anthropic의 연구에서 추론 모델은 힌트를 사용하고도 CoT에서 이를 언급하는 비율이 흔히 20% 미만이었다. outcome 기반 RL로 충실도가 올라가다가 정체했고, reward hacking이 늘어도 그 사실을 말로 드러내는 비율은 늘지 않았다([arXiv 2505.05410](https://arxiv.org/abs/2505.05410)). CoT monitorability를 다룬 논문도 CoT 모니터링이 "유용하지만 fragile"하다고 결론짓는다([arXiv 2507.11473](https://arxiv.org/abs/2507.11473)). 책임성 연구의 합의도 같다. Chan et al.은 agent visibility의 수단으로 **agent identifier, 실시간 모니터링, activity logging**을 제시하며 CoT는 포함하지 않는다([arXiv 2401.13138](https://arxiv.org/abs/2401.13138)). 후속 논문은 채팅 세션 같은 **인스턴스 단위 ID**를 제안한다([arXiv 2406.12137](https://arxiv.org/abs/2406.12137)). EU AI Act Art. 12는 고위험 시스템에 수명 전체에 걸친 자동 이벤트 로그를 요구하고, Art. 19와 26은 **최소 6개월** 보관을 요구한다([Art. 12](https://artificialintelligenceact.eu/article/12/), [Art. 19](https://artificialintelligenceact.eu/article/19/)). 1인용 개인 비서는 Annex III 고위험 시스템이 거의 확실히 아니다. 따라서 이 조항은 법적 의무가 아니라 설계 참고다. 참고할 내용은 사용 기간, 참조한 데이터, 결정에 이른 입력, 검증한 주체를 기록하라는 틀이다.

표준 어휘로는 **OpenTelemetry GenAI semantic conventions**가 사실상 공용어다. `invoke_agent`, `plan`, `chat`, `execute_tool` 연산과 `gen_ai.evaluation.result` 이벤트(`metric.name`, `score`, `score.label`)가 있다. 프롬프트 같은 내용 캡처는 기본값이 꺼져 있는 Opt-In이다([semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md), [events](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-events.md)). 다만 아직 **Development** 상태다. v1.41에서 `execute_tool` 스팬 이름 규칙이 바뀐 것처럼 계속 움직이고 있다([Greptime](https://greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions)). 그러므로 SQLite 정본 스키마를 `gen_ai.*` 이름에 묶으면 semconv 개정마다 마이그레이션이 필요해진다. export 경계에서만 얇게 매핑하는 편이 맞다. Python SDK에는 SQLite exporter가 없지만 `SpanExporter` 인터페이스가 작아 쉽게 구현할 수 있다([OTel Python exporters](https://opentelemetry.io/docs/languages/python/exporters/)). "목표 달성"이나 "사용자 입력 필요" 같은 판단 자체를 위한 표준 필드는 없다. 가장 가까운 방법은 judge를 evaluation으로 모델링해 `metric.name="goal_reached"`, `score.label="needs_user_input"`처럼 기록하는 것이다.

판정 레코드의 모양은 **MLflow Assessment**에서 가져오는 것이 가장 좋다. 필드는 `name`, `value`, `rationale`, `source_type`(`HUMAN`|`LLM_JUDGE`|`CODE`), `source_id`(judge 모델명), `trace_id`/`span_id`, `error`, `metadata`이며, 정답에 해당하는 Expectation을 판정인 Feedback과 분리한다([MLflow feedback](https://mlflow.org/docs/latest/genai/concepts/feedback/)). OpenInference는 `AGENT`/`TOOL`/`EVALUATOR`/`GUARDRAIL` span kind와 `reasoning` 메시지 타입을 정의한다([OpenInference spec](https://github.com/Arize-ai/openinference/blob/main/spec/semantic_conventions.md)). 여기서 `reasoning` 타입은 exporter가 **버려야 할** 대상을 식별하는 데 쓴다. OTel과 MLflow 어느 쪽에도 입력 digest나 evidence ID 목록 필드는 없으므로 AgentOS가 직접 추가해야 한다. 이 두 필드가 핵심이다. digest가 있으면 판정이 나중에 보여준 바로 그 brief와 출력 위에서 내려졌는지 프롬프트 없이 검증할 수 있다. evidence 목록은 판정과 근거를 연결하는데, 두 표준 모두 이 연결을 제공하지 않는다.

## 소유자가 믿음과 증거를 보고 고칠 수 있어야 검사 가능하다고 할 수 있다

"검사 가능한 owner model"의 기준은 이미 1990년대 연구가 세워 두었다. Kay의 scrutable user model은 사용자가 네 가지를 할 수 있어야 한다고 정의한다. 시스템이 자신에 대해 **무엇을 믿는지**, 그 **증거**, 각 구성요소의 **의미**를 보고, 원하면 **바꿀** 수 있어야 한다([Holden & Kay](https://www.semanticscholar.org/paper/The-scrutable-user-model-and-beyond-Holden-Kay/3728db543fb75562c02fe0836885087c7780e555)). 2026년의 상용 제품은 이 기준에 못 미친다. 조사한 제품들은 공통적으로 saved/inferred 두 층, 설정 페이지, 일시정지, 임시 채팅을 제공한다. 그러나 기억 항목에서 원본 대화로 돌아가는 링크는 어디에도 없다. 2026-06의 ChatGPT "Dreaming"은 원자적 목록 대신 합성 요약을 보여주며, OpenAI 스스로 요약이 "모든 것을 포함하지는 않는다"고 인정했다고 보도됐다([TechTimes](https://www.techtimes.com/articles/317840/20260605/chatgpt-memory-dreaming-update-openai-rewrites-personalization-engine-limits-audit-trail.htm), 2차 출처). 이는 읽기 쉬움을 얻는 대신 정정의 정밀도를 잃는 교환이다.

사용자 연구는 무엇을 드러내야 하는지 알려준다. 실제 ChatGPT 사용자 80명의 기억 2,050건을 분석한 결과, 96%가 시스템 생성이었고 28%가 GDPR상 개인정보, 52%가 심리적 추론을 담고 있었다. 사용자 맥락을 충실히 반영한 비율은 약 84%였다([arXiv 2602.01450](https://arxiv.org/abs/2602.01450)). 인터뷰 연구에서는 대다수가 무엇이 기억됐는지 알게 된 뒤 부정적인 기대 위반을 겪었다([CHI '26](https://dl.acm.org/doi/10.1145/3772318.3791635)). 반면 정확한 추론을 맥락과 함께 보여주자 사용자는 불안보다 **호기심**을 보였다. 불편을 만든 것은 부정확한 추론과 제3자로의 전달이었다([arXiv 2605.10013](https://arxiv.org/abs/2605.10013)). 이 결과들을 합치면 추론을 숨기는 것은 답이 아니다. 기억이 생성되는 순간 조용히 알리고("기억함: X · 오늘 대화에서 · 되돌리기"), 정확도 정정과 "이 정보가 어느 AI로 가는가"를 전면에 두는 편이 낫다. UMAP '22 연구에서는 사용자가 기본/중간/고급 중 설명 깊이를 고를 수 있을 때 투명성, 신뢰, 만족이 모두 올랐다([UMAP '22](https://dl.acm.org/doi/pdf/10.1145/3511047.3537685)). TEARS는 편집 가능한 자연어 선호가 실제로 추천을 좌우하게 만들었다([arXiv 2410.19302](https://arxiv.org/pdf/2410.19302)). 두 결과는 각각 결정 기록의 점진적 공개와 "편집하면 실제로 동작이 바뀌는" 기억을 뒷받침한다.

정확히 어떤 UI가 나은지는 아직 모른다. 목록형과 요약형, 알림 유무를 통제 실험으로 비교한 연구는 찾지 못했다. 항목별 신뢰도나 추론/진술 배지를 보여주는 상용 제품도 확인되지 않았다. 신뢰도를 숫자 대신 범주(진술함 / 한 번 추론 / 반복 추론 / 반박됨)로 보여주자는 제안은 연구 근거가 아니라 설계 판단이다.

## 권고: 네 개의 믿음 테이블과 하나의 판단 원장을 기존 스키마 위에 얹는다

결론은 **Build on SQLite, informed by Adopt/Adapt**다. C15에 따른 검토 결과는 다음과 같다. 저장소 내부에는 `memories`, `memory_candidates`, `memory_approvals`, `context_observations`, `current_state_claims`, `turn_provenance`, `tool_events`가 이미 있으므로 새 컴포넌트 대신 확장한다. 표준에서는 W3C PROV 어휘, SQL:2011 bitemporal 패턴, OTel GenAI semconv, RFC 9162 해시 규약을 Adopt한다. stdlib에서는 `sqlite3`, `hashlib`, `json`을 쓴다. 외부 OSS(Mem0, Graphiti, Letta, MLflow)는 정본 소유권이나 저장소 요건 때문에 의존성으로 채택하지 않는다. 다만 MLflow와 Phoenix는 소유자가 원할 때 OTLP export를 받는 선택적 로컬 뷰어로 둘 수 있다. C16에 따른 역할 분담도 분명히 한다. 대화에서 후보 사실을 추출하는 일, 기존 믿음과 조정하는 일(Mem0식 ADD/UPDATE/NOOP 판단), 모순을 감지하는 일, 목표 달성을 평가하는 일은 모두 decision model이 소유자가 선택한 AI에게 맡긴다. AgentOS 코드는 결과를 검증하고 시간 경계와 출처를 붙여 저장할 뿐이며, 정규식이나 범주별 규칙을 두지 않는다.

**owner model**은 다음 구조를 권한다.

| 요소 | 핵심 필드 | 근거 |
|---|---|---|
| `beliefs` (기존 `memories` 확장) | `subject_key`, `value_json`, `kind` (stated/observed/inferred/hypothesis), `status` (current/superseded/retracted/expired/forgotten), `confidence` (모델 보고값, 참고용), `valid_from`/`valid_to`, `recorded_at`/`retracted_at`, `supersedes`/`superseded_by`, `expires_at`, `reason`, `read_only` | Graphiti bitemporal, Wikidata rank, Letta `read_only` |
| `prov_edges` | `subject_id`, `relation` (generated_by/used/derived_from/revision_of/quoted_from/primary_source/attributed_to/invalidated_by), `object_id`, `activity_id`, `at` | W3C PROV, Generative Agents evidence 링크 |
| `payloads` (forgettable) | 개인 내용 원문, 이 테이블만 hard delete + `secure_delete` | Verraes Forgettable Payloads |
| `erasure_log` | `requested_at`, `completed_at`, `requested_by`, `scope`, `counts_json`, `external_recipients_json`, `method`, `backups_pending_until`, `prev_hash` | ICO, EDPB, RFC 9162 해시 규약 |
| profile view | 현재 믿음에서 렌더링한 몇 개의 라벨 block (context 주입용) | Letta block, LangMem profile |

규칙은 여섯 가지다. 첫째, 쓰기는 append-only로 한다. `valid_to`, `retracted_at`, `superseded_by`, `status`만 제자리 갱신을 허용하고, 나머지 필드 변경은 `BEFORE UPDATE` 트리거로 거부한다. 둘째, 단일값 subject에는 `WHERE status='current'` 부분 unique index를 건다. 셋째, 충돌 시 우선순위는 stated > observed > inferred > hypothesis이고 그다음이 최신성이다. stated 믿음은 새 stated 믿음이나 소유자 정정으로만 대체할 수 있다. 넷째, hypothesis(예: "지금 서울에 있을 것")는 만료 시각이 필수이며, 소유자 확인 없이 지속 Memory로 승격하지 않는다(C5). 다섯째, 동사 세 개를 구분한다. supersede/retract는 구간을 닫고, expire는 휘발성 관찰을 TTL로 삭제하며, forget은 파생물 전체를 소거하고 영수증을 남긴다. FTS를 쓴다면 `secure-delete=1`로 생성한다. 여섯째, 배경 통합은 importance 누적 트리거로 실행하고, 결과는 `memory_candidates`로 들어가 기존 승인 흐름을 탄다. 수용 테스트는 LongMemEval의 knowledge update, temporal reasoning, abstention 범주를 소유자 시나리오로 옮겨 만든다. 예를 들어 "이사 후 옛 주소를 현재 주소로 말하지 않는다", "3월 기준으로 무엇을 믿었나에 답한다", "모르는 사실을 지어내지 않는다" 같은 테스트다.

**decision journal**은 기존 `turn_provenance`와 `tool_events`를 확장해 Work 단위 `decision_steps` 원장으로 만든다. 각 행은 `work_id`, `seq`, `step_kind`(plan/delegate/tool_call/judgment/evaluation/outcome/redelegate), `worker`(실제로 관찰된 route·모델·버전, 요청값과 분리), `brief_digest`와 `input_digest`(정규화한 brief와 평가 대상 출력의 sha256), `beliefs_used`(belief ID 목록), `evidence_refs`, `label`(예: `goal_reached`, `needs_user_input`), `stated_rationale`, `confidence`, `source_type`(model_judge/code/owner), `effect_state`(requested/observed/failed/unknown), `error`, `created_at`, `superseded_by`를 가진다. `stated_rationale`은 짧은 문장이고, 충실한 추론 흔적이 아니라 "모델의 주장"으로 라벨링한다. `confidence`는 보정되지 않은 모델 보고값임을 표시한다. 도구 인자와 결과 원문은 저장 전에 redaction을 거쳐 `payloads`에 보관하고, 원장에는 ID와 digest만 둔다. 이는 OTel의 "external storage + reference" 모드와 같은 방식이다. thinking 블록이나 `reasoning` 타입 내용은 저장하지도 export하지도 않는다. 내용 없는 원장 이벤트와 erasure receipt는 stdlib hash chain(`entry_hash = sha256(prev_hash || canonical_json)`)으로 잇고, `BEFORE UPDATE/DELETE` 트리거로 수정을 막는다. chain head는 소유자 Telegram 등으로 주기적으로 anchor할 수 있다. export는 정본 레코드의 JSONL을 기본으로 한다. 선택적으로 OTLP projection(`invoke_agent` → `plan`/`chat`/`execute_tool`, judgment는 `gen_ai.evaluation.result`)과 PROV-JSON을 제공하고, 두 경우 모두 저장 시와 같은 redaction을 적용한다. 화면에서는 점진적으로 공개한다. 1단계는 한 문장으로 무엇을 했는지, 어느 worker가 했는지, 어떤 믿음에 기댔는지를 보여준다. 2단계는 관찰된 단계 타임라인, 3단계는 redaction된 파라미터와 목적지다. 믿음 카드에서 "이 믿음을 쓴 결정"으로, 결정 기록에서 "쓰인 믿음"으로 양방향 링크를 걸어, 결정 기록 안에서 바로 믿음을 정정할 수 있게 한다.

## Conclusion

이 조사에서 드러난 공백은 기술이 아니라 **책임 소재**에 있다. 최신 memory 라이브러리는 추출과 검색 성능을 두고 벤더끼리 경쟁한다. 그러나 출처에서 파생물로의 연쇄 삭제, "틀렸다"와 "더 이상 참이 아니다"의 구분, 판정이 어떤 입력과 어떤 믿음 위에서 내려졌는지에 대한 digest를 모두 갖춘 시스템은 상용과 OSS를 통틀어 하나도 없었다. 이런 기능은 AGENTS.md가 이미 요구하는 Evidence 진실성, Context ≠ Memory, forget/revoke 구분과 정확히 겹친다. 그러므로 AgentOS의 차별점은 더 나은 memory 알고리즘이 아니라 **소유자가 감사할 수 있는 원장**이며, 알고리즘은 교체 가능한 AI에게 맡기면 된다.

남은 불확실성은 세 가지이고, 각각 구현 전에 작은 검증으로 해소할 수 있다. 첫째, LLM이 보고하는 신뢰도에는 선행 연구가 없으므로 처음에는 저장만 하고 UI에서는 범주로 보여준다. 둘째, macOS 파일시스템 아래 계층의 잔존 데이터는 정량 근거가 없으므로 영수증에 best-effort라고 명시한다. 셋째, OTel GenAI semconv는 아직 움직이는 표준이므로 export 매핑만 버전별로 고정한다. 이 세 가지를 정직하게 표시하는 것 자체가 C6가 요구하는 증거 등급 구분의 실천이다.
