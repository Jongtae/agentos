Owner problem statement that motivated the specification (2026-09-26, preserved verbatim):

> 나는 단순 장바구니 담는 기능이 있느냐 아니냐의 문제가 아니라고 봤음. 그런데 지금까지 구현된건 기능을 하나씩 만드는 구조네. decision model을 둔 이유는 이런 기능을 나누려고 한게 아니라 AI가 여러 대안을 찾아가면 동작 할 수 있도록 하는 게이트 역할을 할거라고 본건데, 전혀 다르게 동작 하게 된 것 같음. 검색도 쓸데 없이 민감정보를 보호한다고 이상한 룰을 계속 붙이고 있어. 검색을 하는 대상도 이상한 곳이야. 사실 판단을 하는 애가 대략 어떤 곳을 검색 하도록 할지를 사용자의 사는 곳이나 질문의 카테고리를 판단해서 네이버를 검색 하던, 구글을 하던 하고 그 결과에 따라 적절한 사이트를 찾아서 실제 인터널 웹 브라우저던 어떤 방식이던 처리 할 수 있도록 해야 하는데, 그런 걸 전혀 안하고 그냥 룰 기반의 장치만 하고 있었어.

> 책검색으로만 한정되어 있는데, 내 github 문서들을 보면 다양한 케이스에 대해 대응이 가능하다고 되어 있음. 예를 들면 내 스케줄을 확인해서 리마인드 시켜준다던가, 점심 메뉴를 사전에 준비 해서 내가 물어보면 답해 줄 수 있도록 한다던가, 그런걸 attention이라고 해놨고, 이런걸 해주는 역할이 가능 한 걸 presence 라는 개념을 넣도록 해놨어. 내 취향 내 상황 내 개인 적인 알러지 등을 정말 내 비서라는 secretary 라는 이름에 맞게 해줘야 하고. 내가 필요한 생활용품도 가족(아내)의 장바구니에 담길 수 있도록 가족 에이전트와의 소통도 되어야 하는 거고.

# 요약  
**기존 검색·장바구니 중심 계획을 폐기하고, 개인 비서(Personal AgentOS)로서의 완전한 제품 정의와 실행 모델을 세워야 합니다.** 주요 설계 축은 (1) **비서(Secretary)**—사용자 취향·기록을 유지하며 요구에 대응하는 개인 에이전트, (2) **개인 컨텍스트/메모리**—과거 상호작용과 환경 정보를 보유, (3) **어텐션(Attention)**—사용자의 상황과 목표를 예측·준비하는 능력, (4) **목표 지향 에이전시(Goal-directed Agency)**—주어진 목표를 도구와 계획으로 분해하여 수행, (5) **A2A/가족 협업**—다른 에이전트(예: 가족)의 권한과 요구를 존중하며 협력, (6) **능력 모듈(capabilities)**—검색·일정·브라우저 조작·메일/파일·쇼핑 등 교체 가능한 도구들입니다.  

이 목표를 달성하려면 **에이전트(LLM)와 실행 환경의 역할을 분리**하고, 구체적인 실행 계약을 명세해야 합니다. 에이전트는 사용자의 목표를 받아 행동을 계획·선택하며 결과를 평가하고 재계획합니다. 실행 환경(프레임워크)은 인증·권한·데이터 전송 범위를 강제하고, 도구 호출 결과를 에이전트에 제공하여 **“사용자의 목표가 실제로 이루어졌는가”**를 증거로 판단합니다. 예를 들어, IBM은 AI 에이전트를 “사용 가능한 도구로 워크플로를 설계해 작업을 **자율적으로 수행하는 시스템**”이라 정의합니다. 에이전트는 과거 상호작용을 메모리에 저장하고 계획하며 점점 정밀한 사용자 맞춤형 응답을 제공합니다. 에이전트형 챗봇은 일반 챗봇과 달리 사용자 목표를 장기적으로 계획·완수합니다.

**핵심 제언:**  
- **제품 정의 확인:** 비서는 간단한 검색기가 아니라 사용자 주변 상황과 이력을 이해·대처하는 ‘실시간 비서’여야 합니다. 사용자 일정·선호·알러지 등 퍼스널 컨텍스트를 관리하며 필요한 일을 미리 준비(어텐션)합니다. 예컨대 점심시간 전 알러지 정보를 참고해 메뉴를 추천하거나(Attention), 가족 구성원 장바구니에 품목을 추가하도록 가족 에이전트와 안전히 소통합니다.  
- **규칙과 자율성 분리:** 의사결정 모델은 *“무엇을 할 것인가”*를 판단하고, 실행 환경은 *“이러이러한 작업을 할 권한과 방법이 있는가”*를 엄격히 검사해야 합니다. 모델이 OK를 해도 안전 정책에 위배되면 동작하지 않습니다. 예를 들어, A2A(Agent2Agent) 프로토콜처럼 서로 다른 에이전트 간 통신에도 인증·인가 메커니즘이 필요합니다.  
- **에러 극복과 재시도:** 단순 차단보다는 대안 탐색이 우선되어야 합니다. 처음 검색 결과가 부적합하면 검색어를 변경하거나 다른 제공자를 시도합니다. 예를 들어, “한강”이라는 책 제목이 네이버 검색에선 별로여도, 다른 API나 줄임말 검색을 시도할 수 있어야 합니다.  
- **검증 가능한 성공 기준:** 단순히 에러가 없었다는 것에서 벗어나 **목표 달성의 증거(증거기반 성공 기준)**를 확인해야 합니다. 예를 들어, “장바구니에 추가됨” 메시지 확인, 장바구니 페이지에서 아이템 유무 확인 등이 실제 성공 신호가 됩니다.  
- **점진적 배포:** 첫 단계로 **책 검색→확인→장바구니 추가** 같은 E2E 시나리오를 성공시킨 뒤, 달력·메일 등 다른 시나리오로 확장합니다.

본 문서에서는 위 내용을 근거로 한 **통합 개발 명세(이하 새 명세)**를 기술합니다. 이전 계획과 이슈의 기록은 참고하되, 핵심은 “각 도구가 동작하는가”가 아니라 “모든 단계를 거쳐 사용자의 목표가 실제로 달성되는가”입니다.

## 제품 정의와 지원 범위  
1. **비서(Secretary)** – 단순 명령 이행기가 아니라, 사용자의 생활 전반을 지원하는 개인 에이전트입니다. 사용자의 일정·선호·가족·환경 정보를 반영하여 필요한 일을 예측(Attention)하고 수행합니다. 예를 들어, 사용자가 “점심은 뭐 먹지?” 물으면 현재 시간, 평소 식성·알러지, 주변 음식점 정보 등을 종합해 답합니다. IBM은 AI 에이전트를 “사용 가능한 도구들을 조합해 작업을 자율적으로 수행하는 시스템”으로 정의하며, 이는 비서 역할에도 그대로 적용됩니다.  
2. **개인 컨텍스트/메모리 (Personal Context/Memory)** – 과거 대화·검색·행동 결과, 사용자의 취향·알러지·목록 등 **장기 기억**을 관리합니다. 에이전트가 누적 지식을 이용해 개인 맞춤형 서비스를 제공할 수 있도록, 모든 상호작용은 증거(evidence)와 함께 안전하게 저장됩니다. 메모리 정보는 에이전트가 사용자 요구를 해석하고, 더 나은 답변·알림을 생성하는 데 활용됩니다 (예: 이전에 찾은 음식점 정보 재사용, 반복 일정 리마인드 등). IBM도 “메모리에 과거 상호작용을 저장하고 미래 행동을 계획하는 능력”이 에이전트를 개인화하는 데 중요하다고 설명합니다.  
3. **어텐션 (Attention)** – 에이전트가 **언제 무엇이 필요할지**를 선제적으로 파악하는 능력입니다. 단순 알림(reminder)을 넘어서, 사용자의 상황·시간·장소·목표를 분석해 필요한 행동을 미리 준비합니다. 예컨대 아침에 일어나면 오늘 날씨와 일정에 맞춰 점심이나 외출 준비를 추천하거나, 약속 30분 전 알림을 띄울 수 있습니다. 어텐션 모듈은 사용자에게 필요하지만 요청하지 않은 잠재적 작업(예: 식료품 구매, 일정 확인)도 제안할 수 있습니다.  
4. **목표 지향 에이전시 (Goal-directed Agency)** – 사용자가 자연어로 목표를 제시하면, 에이전트는 이를 **작업(Task)과 하위작업**으로 분해하여 달성합니다. 예를 들어 “책 좀 찾아줘”라는 목표가 들어오면, 에이전트는 (a) 어떤 책인지 확인 → (b) 판매 페이지 찾기 → (c) 장바구니 추가 등으로 단계별로 나눕니다. 에이전트는 IBM 설명처럼 **사용자 목표와 사용 가능한 도구**를 받아서 계획을 세우고 실행합니다. 이 과정에서 필요한 정보를 얻기 위해 검색, 브라우저 조작, 타 에이전트 호출 등 여러 수단을 자율적으로 결합할 수 있어야 합니다.  
5. **가족/타 에이전트 협업 (Family/A2A Collaboration)** – 비서 에이전트는 혼자 동작하지 않고, 같은 AgentOS 플랫폼의 다른 에이전트(예: 가족 구성원)와 협력할 수 있어야 합니다. 예를 들어, 사용자가 “아내 장바구니에 세탁세제 넣어줘”라고 하면, 에이전트는 자신의 권한으로 아내 계정을 조작하는 것이 아니라, 아내 에이전트에게 요청(task delegation)하여 처리합니다. 이를 위해서는 **Agent2Agent(A2A) 프로토콜**과 유사한 개방형 표준에 따라 메시지를 주고받아야 합니다. 구글·IBM 등은 A2A를 “다양한 생태계의 에이전트들이 서로 통신하고 정보를 공유하는 개방형 프로토콜”로 정의합니다. 이 협력을 통해 가족끼리 장바구니 공유, 공동 일정 조율, 메시지 전달 등이 안전하게 이루어지도록 합니다.  
6. **능력 모듈 (Capabilities)** – 위의 기능들을 실제로 수행할 구체적 도구들입니다. 예를 들어 **웹 검색**, **인터넷 공개페이지 읽기**, **브라우저 조작(로그인·클릭·입력)**, **캘린더 조회/추가**, **메일/파일 접근**, **쇼핑(상품 검색/장바구니)** 등이 이에 해당합니다. 각 능력은 **모듈화 가능**하며, 새로운 제공자·서비스로 교체할 수 있습니다. 예를 들어 검색은 네이버 API, 브레이브 Search API, 자체 SearXNG 서버 등 다양한 공급자를 사용할 수 있습니다(표1 참고). 에이전트는 필요한 정보를 얻기 위해 상황에 맞게 적절한 모듈을 선택·연결합니다.

| **능력 (Capability)** | **역할** | **예시 제공자·서비스** |
|---|---|---|
| **웹 검색** | 키워드나 질문으로 정보 탐색 | 네이버/OpenAPI(한국어), 구글 맞춤검색(글로벌), Brave Search API(익명 검색), 자체 SearXNG(다중 엔진) 등 |
| **페이지 읽기** | 검색 결과나 링크 클릭 후 페이지 내용 추출 |   웹 크롤러/스크레이퍼 (BeautifulSoup, Playwright 등)  |
| **브라우저 조작** | 로그인, 검색창 입력, 버튼 클릭 등 |  Playwright 등의 헤드리스 브라우저 자동화  |
| **일정/캘린더** | 개인 일정 조회/알림 |  구글 캘린더, 네이버 캘린더 API 등  |
| **메일/파일** | 이메일 읽기/쓰기, 개인 파일 접근 |  Gmail API, OneDrive/Google Drive API  |
| **쇼핑/장바구니** | 상품 검색, 상품 페이지 탐색, 장바구니 조작 |  교보문고·쿠팡 등 서점 API, 웹 UI 자동화  |

*표1: 주요 능력 모듈과 예시 제공자. 필요에 따라 새로운 모듈을 추가하거나 교체할 수 있음.*

에이전트는 위 도구들을 조합해 목표를 달성해야 합니다. 예를 들어 책을 찾을 때는 웹 검색 → 결과 페이지 읽기 → 브라우저 조작(장바구니 추가) 순으로 진행하며, 중간 결과마다 메모리와 리저닝을 거쳐 대상을 확인합니다. 이 과정에서 **제한된 범위 내에서만 자율성**이 부여되고, 그 외에는 사용자 동의 또는 실행 환경의 제어를 받습니다. 예를 들어 새로운 검색 API를 사용하거나 장바구니 결제 같은 작업은 사전에 사용자의 허가 설정 또는 수동 승인이 필요합니다.

## 1차 개발 명세 (Normative Requirements)  
제품 정의를 바탕으로, 에이전트와 실행 환경의 역할을 명확히 분리한 실행 계약을 정리했습니다.

- **모델(에이전트) vs 실행 환경 책임:** 모델은 **“할 일”**을 계획·결정합니다(어떤 작업을 언제 호출할지 선택). 실행 환경은 **“할 수 있는지”**를 검증합니다(인증, 권한, 민감도 검사, 비용 평가). 예를 들어, 모델이 검색어를 생성하면 실행 환경이 해당 검색어와 제공자를 확인하여 전달합니다. 모델이 클릭을 요구해도 해당 버튼이 민감한 작업(결제 등)이면 실행 환경이 이를 차단하거나 사용자 확인을 거칩니다. 이 분리는 이미 `decision-layer` 문서에도 제시된 원칙입니다.  
- **결정 모델(Decision Model)의 역할:** 모델은 사용자의 목표를 받으면 다음 행동(검색 실행, 페이지 클릭, 추가 질문 등)을 **반복적으로 선택**합니다. 각 단계마다 도구 실행 결과를 받고, 목표 달성 여부를 판단해 계속하거나 종료합니다. 애착통(IBM)에서 설명하듯, 모델은 초기 목표와 사용 가능한 도구를 받아 **계획(goal decomposition)** 을 세우고, 필요한 정보를 얻기 위해 외부 도구(검색, DB, 기타 에이전트 등)를 호출할 수 있어야 합니다. 중요한 것은, 각 행동을 선택할 때 현재 메모리와 어텐션 정보(문맥)를 고려한다는 점입니다.  
- **권한 및 동의(Authority/Consent) 체크:** 모든 정보 교환과 상태 변경에는 명확한 권한 경계가 있어야 합니다. 예를 들어, 사용자 동의 없이 개인 비밀번호, 은행정보, 사적 문서를 전송해서는 안 됩니다. 반면 공개 정보 검색이나 책 상품 검색 같은 비민감 활동은 미리 허용된 범위에서 자동으로 진행할 수 있습니다. A2A 통신도 마찬가지로, 각 에이전트가 **인증 토큰**과 **에이전트 메타데이터**(에이전트 카드)로 상호 신원을 확인하고, 권한 허용 범위 안에서만 작업을 위임해야 합니다. 구글은 A2A 프로토콜을 설계할 때 “기본적으로 보안되도록 설계했다(Secure by default)”고 밝힙니다.  
- **검색 제공자 선택 규칙:** 모델은 사용자의 언어, 지역, 맥락에 따라 검색 제공자를 선택할 수 있어야 합니다. 예를 들어 한국어 서적 검색 시 우선 네이버/카카오 API를, 일반 정보검색 시 브레이브/구글을 시도하도록 합니다. 모델이 한 검색으로 답을 얻지 못하면 **다른 제공자**나 **검색어 수정**을 시도할 수 있어야 합니다. 제공자 선택권과 관련하여, 사용자(제품 소유자)는 기본 제공자 목록(네이버, 브레이브, 자체 SearXNG 등)을 설정하며, 새로운 제공자 추가는 나중에 승인을 받는 것으로 명시합니다. (예: “[검색 공급자] 다음 중 골라줘” 같은 추가 명령 대신, 시스템 설정을 통해 관리.)  
- **재시도 및 탐색 정책:** 만약 검색 결과가 무관하거나 불충분하면, 에이전트는 즉시 종료하지 않고 **대체 전략**을 실행해야 합니다. 구체적으로:  
  - **검색어 수정:** 예를 들어, 너무 긴 문장은 핵심 키워드만 남겨 다시 검색하거나, 초성과 같이 변형해서 시도합니다.  
  - **제공자 전환:** 초기 검색이 원하는 정보를 못 주면 즉시 다른 검색 제공자(API)를 호출합니다.  
  - **체계적 탐색:** 검색 결과가 너무 일반적이면 (예: 인기 신간 전체 리스트만 나옴) 판매 사이트의 내부 검색 기능으로 전환합니다.  
  이러한 탐색 과정에서, 같은 수단으로 동일 결과만 반복하지 않도록 해야 합니다.  
- **성공/실패 판정 기준 (Evidence-based):** 단순히 “에러가 발생하지 않았다”는 것으로 끝내지 않습니다. 목표 달성의 증거를 요구합니다. 예를 들어 “장바구니 추가” 목표라면 실제로 해당 서점의 장바구니 페이지에서 해당 상품이 담긴 것이 화면에 보여야 성공입니다. 검색만 했다면, 제품 정보(제목/저자/가격)가 목적에 부합하는지를 확인하고 사용자에게 보고해야 합니다. 일반적인 기준은 **환경의 최종 상태(observable state)** 와 모델의 응답 내용이 일치하는지입니다. (예: 사용자가 “장바구니에 넣었어”라는 답변을 받았으면, 실제 장바구니에 리스트가 있어야 함.)  
- **실패 모드 및 복구:** 예외 상황별로 복구 방안을 정의합니다. 예컨대  
  - *로그인 필요:* 로그인 세션이 없으면 에이전트는 사용자에게 알림을 보내거나 재로그인을 시도합니다.  
  - *페이지 오류:* 페이지 로드 실패 시 재시도 혹은 다른 링크 탐색.  
  - *예상치 못한 구조:* 버튼이 예상 위치에 없다면 DOM 탐색해서 찾거나, 무한 스크롤 중이면 요소를 검색합니다.  
  - *권한 부족:* 특정 데이터 접근이 안 되면 “권한이 필요함”으로 보고하고 중단합니다.  
  위 사례별 복구에 실패하면, 사용자에게 “이 작업은 할 수 없다”라고 명확히 설명하고 중단합니다(예: “장바구니는 지원하지 않으므로 책 정보만 제공”). 단, 중간에 실패하더라도 이미 얻은 정보는 보고하고, 다음 수행을 제안할 수 있어야 합니다.

## 우선 순위 배포 계획  
우선순위는 “기능 단위”가 아니라 “E2E 시나리오”로 잡아야 합니다. 첫 번째 목표는 **책 검색→확인→장바구니 추가** 시나리오입니다. 이를 충족해야 시스템이 진짜 작동하는 비서로 인정받습니다. 세부 단계와 검증 항목은 다음과 같습니다.

1. **시나리오 설명:** 사용자가 텔레그램으로 책 제목을 요청하면, 에이전트는 허용된 검색 수단으로 상품 페이지를 찾은 뒤 판매 사이트(예: 교보문고)에서 동일 책인지 확인하고, 가능하면 장바구니에 추가한 후 결과를 리턴합니다.  
2. **성공 관찰 (Success signals):**  
   - 상품 페이지나 API 응답에서 *책 제목, 저자, 판본* 등이 사용자의 요청과 일치하면 확인 완료.  
   - 장바구니 페이지나 API에서 해당 상품이 추가된 것이 확인되면 추가 완료. (예: “장바구니에 추가되었습니다” 확인 메시지, 혹은 장바구니 리스트에서 제목 일치)  
   - 에이전트의 최종 응답이 실제 작업 결과와 일치해야 합니다(“장바구니에 담았습니다”라고 할 경우 실제 담김).  
3. **실패 관찰 (Failure signals):**  
   - 책을 찾지 못했거나 혼동 가능성이 있으면 모델이 추가 질문 혹은 재검색을 제안.  
   - 로그인이나 권한 문제 시 “로그인이나 권한이 필요함”을 알림.  
   - 네트워크/페이지 에러 시 재시도 시도, 안 되면 사용자에게 알려줌.  
4. **검증 및 테스트:**  
   - **단위 테스트:** 검색 모듈, HTML 파싱, 권한 검사 등 개별 컴포넌트에 대해 모의 데이터를 이용한 유닛 테스트를 작성합니다.  
   - **통합 테스트:** 실제 API 키나 셋업된 테스트 환경을 이용해 검색→페이지→장바구니 기능을 흐름별로 검증합니다(예: 헤드리스 브라우저로 장바구니 추가까지 시뮬레이션).  
   - **라이브 시뮬레이션:** 개발 중 실제 텔레그램 봇을 통해 *소규모 실제 사용자 입력*을 받아 에이전트 동작을 관찰합니다. (예: **모의 사용자**가 “책 제목: 왕좌의 게임” 입력)  
   이때 모델의 선택 및 도구 호출 로그도 함께 기록하여, 단계별 행동이 명세에 맞는지 확인합니다.  
5. **이슈 처리:** 기존 이슈(#650~#652 등)는 새 명세에 맞게 재정의·연결합니다. 예를 들어, #650(일반 검색어 민감도 오류)은 검색 모듈 개선 과제로 삼고, #651(장바구니 기능 없음 응답 수정)은 에러 복구 플로우의 일부로 통합, #652(검색 개선)은 다중 제공자 전략으로 확장합니다. 세 이슈 자체는 기록으로 남기고 닫되, 구체 작업은 아래 이슈 목록에서 다시 정의합니다.

## 전환(Migration) 계획  
기존 저장소의 코드와 문서를 가능한 재사용하되, 새 명세에 부합하도록 구조를 수정합니다.

- **코드 리팩터링:**  
  - `LocalTools.search` (현재 Bing RSS 고정) → **다중 제공자 검색** 지원. 검색 요청 시 사용 언어/문맥에 따라 동적 선택할 수 있도록 입력값을 바꿀 수 있어야 합니다.  
  - `lookup_term_sensitivity` (민감도 판단) → 평범한 상품명은 통과시키도록 로직 수정. 기존 이슈(#650)에서 지적된 *“모호성, 낮은 확신도”* 문제를 해결합니다.  
  - `run_agent` 루프 → 목표 달성 시점 판정을 강화. 단순 도구 호출 성공이 아닌, 성공 신호(상품 확인, 장바구니 상태)를 기준으로 `succeeded`를 결정합니다.  
  - `Capabilities` 구성 → 페이지 읽기와 브라우저 도구를 분리하고, 인증이 필요한 도구(브라우저 자동화)도 포함합니다. 현재 “공개 페이지 읽기” 모드와 “쇼핑 모드”를 범용 도구로 재구성해야 합니다.  
  - `delivery-plan.yaml` → 초기 단계 목표(책 검색→장바구니)를 명시적으로 추가하고, 기존 “장바구니 없음, 읽기 전용” 제약은 제거하거나 조건부로 변경합니다.  
- **문서 정리:** `AGENTS.md`, `Presence`, `Attention` 등의 문서에 기술된 높은 수준의 아키텍처와 UX 원칙을 유지하되, “읽기 전용 에이전트”라는 해석 대신 **목표 달성 에이전트**를 전제로 한 설명으로 업데이트합니다. 과거 의도와 달라진 부분(검색 제한, 장바구니 정책 등)은 문서에 주석으로 남겨 두어, 왜 변경했는지 추적할 수 있게 합니다.  
- **테스트 및 기록 보존:** 기존 테스트 코드는 새로운 모듈로 재사용하거나 수정하여 유지합니다. 구현 중 발견된 버그 사례(예: 낮은 확신도, 페이지 스크립트 오류 등)는 회귀 테스트 케이스로 추가하여 반복 방지합니다. 모든 작업은 계속 히스토리에 남겨두어 **무엇이 왜 폐기되었는지** 추적할 수 있어야 합니다.

## 보안·개인정보 제약 및 동의 UX  
에이전트가 사용자 데이터를 다룰 때는 엄격한 프라이버시와 동의 관리가 필요합니다.  
- **소유자 제어:** 사용자는 설정 메뉴를 통해 에이전트의 권한 범위를 지정할 수 있어야 합니다. 예: “내 캘린더 읽기/쓰기”, “비공개 문서 접근 금지” 등. 동의되지 않은 작업은 에이전트가 시도하지 않습니다.  
- **동의 UI:** 브라우저로 로그인 또는 민감 정보 전송이 필요할 때, 텔레그램 챗으로 명확한 허가 메시지를 띄웁니다. 예: “OOO님, `daum.net`에 [검색어/비밀번호] 정보를 전송하려고 합니다. 허용하시겠습니까?”. 사용자의 명시적 동의(버튼 클릭) 없이는 진행하지 않습니다.  
- **데이터 처리:** 인증 정보나 개인 데이터는 안전하게 암호화 저장하며, 모델 프롬프트나 로그에 노출하지 않습니다. 예를 들어 Playwright로 세션을 유지할 때 쿠키는 모델과 공유하지 않고, 실행 환경 내에만 저장합니다.  
- **최소 권한 사용:** 에이전트는 필요한 최소한의 데이터만 요청합니다. 예를 들어, 책 검색에는 서점 사이트의 공개 API나 RSS만 사용하고, 사용자의 개인 신용정보는 전혀 다루지 않습니다. 애초에 결제 등 민감 작업은 범위 밖으로 두고, 관리자(사용자)가 별도 승인한 도구로 남깁니다.  
- **감사 로깅:** 모든 도구 호출과 상태 변경은 로컬 로그에 기록하여, 후에 사용자가 “에이전트가 이 작업을 했나?” 확인할 수 있게 합니다. 로그에는 수행된 HTTP 요청, 클릭한 버튼, 전송된 파라미터 등이 포함되며, 로그는 앱 내부에 암호화된 채로 보관하거나 (운영자 설정 시) 외부 감사용 모니터링 서버에 전송합니다.

## 결론  
이번 재편의 핵심은 **“각 도구의 구현”이 아니라 “도구들을 통과하여 사용자의 목표가 실제로 이루어지는지”**입니다. 기존 이슈들은 유용한 참고지만, 이슈 자체가 목표 달성을 보증하지는 않습니다. 예를 들어 #650, #652를 고쳐도 검색·탐색이 실패하면 의미가 없습니다. 

따라서 새 명세의 완료 기준은 “최종 상태에서 목표 달성 여부”입니다. Anthropic도 에이전트 평가 시 실제 환경 상태를 점검할 것을 권장합니다. 이를 위해 처음에는 실제 모델을 투입하여 스몰 테스트를 하며, 목표 이행 가능 여부를 확인합니다. 

첫 작업은 단순 기능 추가가 아니라 **“책 한 권을 끝까지 처리하는 전체 경로를 만들고 검증하는 것”**이어야 합니다. 이를 통해 에러의 원인이 프롬프트인지, 도구 결함인지, 설계 한계인지 분리할 수 있으며, 남은 구현 방향을 명확히 할 수 있습니다. 

궁극적으로, 백로그 정리의 성공 기준도 “문서가 깔끔해졌다”가 아닙니다. **“사용자가 요청한 목표를 에이전트가 실제로 완료했다”**를 목표로 삼아야 합니다. 이번 설계 변경과 이슈 재정비가 그 전제 조건이 될 것입니다.

**주요 참고:** IBM/Google의 AI 에이전시 개념을 바탕으로 설계 방향을 잡았으며, 새로운 AgentOS 설계 문서 및 도구 구현 로직을 따르는 형태로 명세를 작성했습니다.
