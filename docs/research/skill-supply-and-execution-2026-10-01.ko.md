# AgentOS 스킬 공급과 재사용 가능한 실행 — 논의 정리와 구현 준비

작성일: 2026-10-01  
상위 이슈: [SKILL-SUPPLY-01 #959](https://github.com/Jongtae/agentos/issues/959)  
기준 코드: `4e518550b13e13c3cd06cdf05987948ac8169fca`  
영문 기준 명세: [Supplied Skills and Reusable Execution](../skill-supply-execution-preparation.en.md)

> **사용자가 처음부터 가르치고 실패하게 하지 않는다. 이미 배포된 능력을 먼저 받아 쓰고, 환경에 맞춰 연결하며, 없는 부분만 탐색하고 개선한다.**

이 문서는 소유자와의 대화를 정리한 한국어 동반 문서다. 구현 범위와 기술 계약의 기준은 위 영문 명세다. 현재 승인된 작업은 문서와 GitHub 이슈를 만드는 구현 준비이며, 런타임 구현·패키지 설치·모델 변경·실제 장바구니 조작·배포는 시작하지 않는다. 현재 개발 목표와 순서도 바꾸지 않는다.

**후속 논의 반영:** 13절과 영문 명세 18절에 기존 기능 보존, 인터페이스 우선 설계, 디자인 패턴의 적용 위치와 검증 비용 제한을 추가했다. 기존 구현을 교체하거나 테스트 범위를 무조건 늘리는 방향이 아니다.

## 1. 어떤 문제를 해결하려는가

출발점은 이마트 장바구니였다. 비슷한 요청인데도 매번 사이트, 검색 경로, 로그인 상태, 상품 선택, 버튼 위치와 완료 조건을 다시 판단하면 실행이 흔들린다. 메인 AI가 매 요청마다 수행 방법과 프롬프트를 새로 만드는 부담도 반복된다.

같은 문제는 AgentOS 자체 관리에서도 나타날 수 있다. 가족 비서 만들기, Main AI 바꾸기, 로그인 공유하기를 사용자의 말에 맞춰 수행하더라도, 그 기능을 올바르게 사용하는 방법까지 매번 발명할 필요는 없다.

그래서 나온 방향은 **수행 능력을 컴포넌트처럼 재사용한다**는 것이다. 다만 컴포넌트마다 별도 AI를 실행하는 것이 목표는 아니다. 반복 가능한 방법은 스킬로 제공하고, 독립적인 탐색·판단이 실제로 필요한 작업만 전문 에이전트에 맡긴다.

## 2. 가장 중요한 수정: 학습보다 공급이 먼저다

초기 논의는 성공과 실패 경험을 스킬로 축적하는 데 무게가 실렸다. 소유자는 여기에 중요한 조건을 추가했다.

**누군가 이미 이마트 스킬을 만들었거나, 이마트가 공식 배포할 수도 있다. 각 사용자가 같은 시행착오를 반복할 이유가 없다.**

따라서 기본 순서는 다음과 같다.

1. 이미 설치되었거나 기본 제공되는 적합한 스킬을 사용한다.
2. 필요한 능력이 없으면 공식·공개 공급원에서 호환 가능한 패키지를 찾는다.
3. 출처·버전·필요 도구·실행 환경을 확인해 사용자의 환경에 연결한다.
4. 공급된 능력으로 해결되지 않는 부분만 일반 탐색으로 처리한다.
5. 개선 가치가 확인된 경험은 나중에 스킬 수정 후보로 남긴다.

매 요청마다 마켓을 검색하지 않는다. 한 번 도입한 버전은 재사용하고, 실제 기능 부족이나 업데이트·복구가 필요할 때 공급원을 다시 확인한다. 처음 사용자도 배포된 스킬로 첫 작업을 수행할 수 있어야 한다.

이 준비에서 공식 이마트·SSG 스킬이 실제 배포되어 있다고 확인한 것은 아니다. 공식 배포는 지원해야 할 공급 형태이며, 특정 패키지의 존재와 호환성은 별도 확인 대상이다.

## 3. 스킬·도구·에이전트를 구분한다

| 구분 | 맡는 일 | 예시 |
| --- | --- | --- |
| 개인 비서 / Main Agent | 사용자 의도, 대화 맥락, 제약과 최종 답변 | “아내 비서에게 장을 봐 달라고 해줘”를 이해한다. |
| Skill | 반복 가능한 수행 방법과 참고자료 | 상품을 식별하고 장바구니 변화를 확인하는 방법 |
| 전문 Agent | 독립적인 판단과 긴 작업이 필요할 때 실행 | 복잡한 상품 비교를 별도 맥락에서 수행한다. |
| Capability | 실제 시스템·서비스 기능 | 브라우저 읽기·클릭, 설정 조회·변경 |
| AgentPackage | 배포·버전·호환성과 생명주기 단위 | 스킬과 AgentOS 실행 연결 정보를 묶는다. |
| Kernel / 서비스 | 상태·세션·권한·실행 기록·복구 | 실제 설정값과 실행 결과의 출처를 관리한다. |

스킬 가져오기, MCP 도구 연결하기, A2A 에이전트에 일 맡기기는 서로 다르다. 마켓에서 발견했다는 이유로 다른 플랫폼의 계정 권한까지 가져올 수 있는 것은 아니다.

첫 구현에서는 **같은 비서 실행 안에서 필요한 스킬을 읽는 방식**을 우선한다. `Shopping Agent → Emart Agent → Browser Agent → Verifier Agent`를 모두 만드는 것은 이번 범위가 아니다.

## 4. 기존 AgentOS를 어떻게 활용하는가

기준 코드에는 역할·도구를 선언하는 `manifests.py`, 로컬 선언 패키지를 관리하는 `PluginRegistry`, API·CLI 실행 경로, 브라우저 세션, 설정 관리와 가족 로그인 공유 기능이 있다. 근거와 정확한 한계는 [영문 명세의 기준 코드 표](../skill-supply-execution-preparation.en.md#3-baseline-existing-seams-and-actual-gaps)에 연결했다.

하지만 현재 패키지는 기존 host action을 선언하는 구조이며, 임의 코드를 실행하는 스킬 플랫폼은 아니다. `delegate_agent`도 읽기 전용 자식 실행을 만들고 브라우저·설정 실행기를 넘기지 않는다. 역할만 하나 추가한다고 행동 전문 에이전트가 완성되는 것은 아니다.

따라서 기존 패키지·실행 경로에 공개 스킬 표현과 필요한 리소스 로딩을 연결한다. 별도의 패키지 레지스트리, 권한 데이터베이스, 기억 저장소, 오케스트레이터를 새로 만드는 방향은 피한다.

기존 `#343`은 확인 당시 `closed / not_planned`였다. 이번 준비는 그 내용을 참고하는 좁은 후속 범위이지, 과거 전체 마켓플레이스 계획을 다시 활성화하는 작업이 아니다. `.claude/skills`에 개발 보조 스킬을 넣은 `#548`도 제품 런타임 스킬 지원과 구분한다.

## 5. 관리 스킬과 쇼핑 스킬의 공통 원리

### AgentOS 관리 스킬

`agentos-management`는 기존 `SettingsOrchestrator`와 실제 서비스의 조회·변경 기능을 사용한다. 프롬프트가 설정 파일이나 내부 데이터베이스를 직접 고치게 하지 않는다.

**Main AI 변경:** 요청한 경로, 저장된 경로, 실제 적용 경로, 실행 준비 상태, 실제 사용이 관찰된 상태를 구분한다. 설정값만 저장하고 새 모델로 실행까지 검증했다고 말하지 않는다. 현재 Work와 다음 Work에 어느 경로를 적용할지는 명시적인 계약으로 정한다.

**가족 비서 생성:** 인스턴스 준비, 설정 링크 준비, 가족의 연결 완료, 사용 가능 상태를 나눈다. 링크가 만료되었다고 이미 연결된 비서를 미연결로 판단하지 않는다. 중단·재시도 때 비서를 중복 생성하지 않는다.

**로그인 공유:** 어느 비서에서 어느 비서로 어떤 사이트를 공유하는지 확인하고, 실제 전달·대기·회수 중·회수 완료를 서비스 상태로 보고한다. 표시 이름이 같으면 내부 식별자를 확인한다.

기존 `#918`의 “사용자가 직접 요청한 설정은 적용 후 알림·되돌리기” 방향과 현재 구현을 대조한다. 스킬을 넣으면서 불필요한 확인창을 다시 늘리지 않는다. 추론으로 제안한 변경의 필요한 확인과 실제 되돌릴 수 있는 범위는 유지한다.

### 쇼핑과 사이트 스킬

공통 쇼핑 스킬은 상품·옵션·용량·수량·사용자 제약과 완료 조건을 다룬다. 사이트별 스킬은 검색과 탐색 방법, 상품 주변의 동작, 결과를 확인하는 위치 등을 다룬다.

“하나 더 담아줘”, “총 하나로 맞춰줘”, “하나는 있도록 해줘”는 다른 요청이다. 기존 장바구니 상태를 읽고 필요한 변화만 수행해야 한다. 상품과 옵션을 확인하고, 실행 후 장바구니를 다시 관찰해 요청한 변화가 있었는지 확인한다.

버튼을 눌렀다는 사실이나 AI가 작성한 `cart_present: true`만으로 성공을 확정하지 않는다. 응답이 끊겼을 때는 다시 누르는 것이 아니라 현재 상태부터 확인한다. 다른 가족 비서가 같은 장바구니를 바꿔 결과를 구분할 수 없다면 불확실하다고 남긴다.

두 기능의 공통 원리는 **행동을 반복하는 것이 아니라, 아직 충족되지 않은 목표를 현재 상태에서 이어서 수행한다**는 것이다.

## 6. 방법은 기억하고, 사실과 권한은 다시 확인한다

사이트를 사용하는 방법은 재사용한다. 하지만 지금 로그인되어 있는지, 상품 가격·재고가 무엇인지, 장바구니 수량이 얼마인지, 공유 권한이 살아 있는지는 현재 상태에서 확인한다.

사용자의 선호는 개인 Memory, 사이트 수행 지식은 Skill, 중단된 작업의 상태는 Work에 속한다. 서로 연결할 수 있지만 같은 종류의 기억으로 취급하지 않는다.

가족끼리 같은 공개 스킬을 쓸 수 있다는 것이 같은 계정·개인 이력·권한을 공유한다는 뜻도 아니다. 현재 쿠키 기반 로그인 공유를 사이트 사업자가 발급한 장바구니 전용 권한처럼 설명하지 않는다. 계정 소유 측에서 제한된 작업을 대신 수행하는 위임 방식은 후속 가능성이지만 기존 A2A 이슈 `#661`과 연결할 별도 범위다.

## 7. 공개 공급원은 어떻게 받아들이는가

이번 준비에서 확인한 1차 문서와 사용 목적은 다음과 같다. 링크별 세부 출처는 [영문 명세의 참고자료](../skill-supply-execution-preparation.en.md#16-evidence-and-public-references)에 있다.

| 공급·구현 | AgentOS에서 검토할 부분 |
| --- | --- |
| Agent Skills | 공개 `SKILL.md` 표현과 필요한 리소스 구조 |
| Microsoft Agent Framework | `SkillsProvider`의 로딩·리소스 공급 구현 |
| OpenAI 플러그인, Claude 마켓플레이스, Gemini CLI 확장 | 공개된 패키지와 형식의 호환 가능한 부분 |
| skills.sh, Hermes Skills Hub | 여러 출처에서 스킬을 발견·가져오는 방식 |
| MCP Registry | 새 도구의 메타데이터 발견; 스킬 자체나 실행 권한과는 구분 |

이 목록은 “AgentOS에서 모두 작동한다”는 목록이 아니다. 첫 범위는 기본 제공 스킬과 **실제 외부 제작 스킬 하나를 받아 쓸 수 있는 공급 경로**다. 모든 마켓 연결을 먼저 완성하지 않는다.

정확한 라이브러리·버전·라이선스·유지보수 상태와 실행 환경 적합성은 첫 하위 이슈에서 작은 호환성 검증으로 결정한다. `skills-ref`는 공식 README에서 데모용이라고 밝히므로 곧바로 프로덕션 의존성으로 선택하지 않는다.

## 8. 경계는 명확하게, 사용자 부담은 작게

처음에는 지침과 리소스로 구성된 패키지가 기존 AgentOS 도구를 쓰도록 한다. 임의 스크립트, 셸, 훅, 외부 실행 서버가 필요한 패키지는 지원하지 않는다고 구분한다. 필수 스크립트를 빼고 정상 호환이라고 표시하지 않는다.

이미 검토되고 활성화된 스킬을 읽을 때마다 사용자에게 묻지 않는다. 처음 도입하거나 실행 권한이 달라질 때 필요한 판단은 패키지 정책과 현재 권한에서 처리한다. 공식 출처, 파일 무결성, AgentOS 호환성, 실제 행동 검증은 각각 구분해서 보여준다.

버전은 Work에 고정한다. 업데이트가 진행 중인 작업의 방법을 몰래 바꾸면 안 된다. 스킬이 이미 모델 맥락에 들어간 뒤 비활성화되어도 이후 패키지 기반 행동이 차단되는지 실행 경로에서 확인해야 한다. 스킬 파일을 못 읽게 하는 것만으로 권한 회수가 끝났다고 판단하지 않는다.

스킬을 제거해도 사용자의 기억·결과물·필요한 실행 기록은 기존 정책에 따라 남는다. 롤백은 패키지 내용을 복구하는 것이지 이미 철회한 권한이나 외부에서 완료된 행동을 되돌리는 보장이 아니다.

## 9. C16은 명시적으로 정리한다

현재 C16에는 사이트별 코드뿐 아니라 task-named guidance 금지도 포함되어 있다. 따라서 “스킬 파일이니까 당연히 허용된다”고 해석하면 안 된다.

제안은 **핵심 런타임의 숨은 시나리오 분기**와 **발견·검토·버전 관리가 가능한 전문 지식 패키지**를 구분하는 것이다. 스킬이 사이트 지식과 힌트를 갖는 것은 허용하되, 동일한 AgentOS 실행 기능·권한·근거 경로를 사용하게 한다.

이 준비 문서는 원칙을 실제로 변경하지 않는다. 첫 하위 이슈에서 헌법·개발 지침·회귀 테스트를 함께 대조하고 변경 범위를 확정한다.

## 10. 구현 준비 이슈와 순서

## 11. 무엇으로 효과를 판단하는가

기존 AgentOS와 같은 모델·도구 조건의 스킬 적용 버전을 비교한다. 새 사용자의 첫 요청과 이미 사용해 본 반복 요청을 구분한다. 스킬 개수와 에이전트 개수는 성과 지표가 아니다.

확인할 것은 실제 목표 달성, 잘못된 완료 보고, 중복·요청하지 않은 행동, 사용자 개입 횟수, 응답 시간, 모델·도구 호출량, 공급원 조회와 유지보수 비용이다. 스킬을 찾고 검토한 비용도 포함한다. 측정하지 못한 사용량은 모른다고 남긴다.

상품·수량 변경, UI 변화, 로그인 만료, 응답 유실·재시작, 모델 교체, 공유 회수, 로드 후 스킬 비활성화, 두 번째 사이트를 사례에 넣는다. 실제 도구 관찰을 정답 근거로 삼고 모델의 자체 성공 보고를 정답으로 쓰지 않는다.

이 사례 목록은 매 수정마다 전체 모델·사이트를 실사용 검증하라는 지시가 아니다. 기존 기능 보존은 #961부터 확인하고, #964는 앞서 확보한 근거를 재사용한다. 변경 경계별 검증 범위와 비용 제한은 아래 13절을 따른다.

개발은 기존 테스트·평가 도구와 가짜 서비스·격리된 데이터로 검증한다. 실제 모델·사이트 검증은 계정, 허용 행동, 정리 방법, 호출·시간 예산을 정한 별도 승인 범위다. 이 준비에서 실제 이마트 성공률이나 비용 개선을 측정하지 않았다.

## 12. 프로젝트의 발전 방향

AgentOS가 앞서갈 지점은 모든 스킬을 독자적으로 만드는 데 있지 않다.

**이미 만들어진 능력을 처음부터 공급받고, 사용자의 환경에 정확히 연결하며, 모델을 바꿔도 수행 지식과 작업 연속성을 유지하는 것**이 핵심이다.

경험을 통한 학습은 그다음이다. 배포된 능력이 부족한 부분을 수정 후보로 만들고, 실패 조건과 독립적인 검증을 거쳐 새 버전으로 발전시킨다. 한 번 성공했다고 자동으로 신뢰하는 스킬로 승격하거나 개인 실행 기록을 공개 패키지에 넣지 않는다.

궁극적인 제품 약속은 다음과 같다.

> “어느 모델을 쓰든, 이미 잘 만들어진 능력을 내 비서가 받아 쓴다. 같은 설명과 같은 실패를 반복하지 않고, 무엇이 실제로 끝났는지도 확인할 수 있다.”

이번 산출물은 그 방향을 구현하기 위한 준비 명세다. 스킬 실행 기능이나 새 마켓이 이미 구현되었다는 주장은 아니다.

## 13. 후속 결정: 인터페이스를 먼저 설계하고 검증 비용을 제한한다

소유자는 기존에 잘되던 이마트 장바구니 등이 새 구조 때문에 망가질 가능성과, 이를 검증한다며 많은 토큰을 소비할 가능성을 지적했다. 이어서 인터페이싱과 기본 설계, 디자인 패턴 검토가 먼저라고 정리했다. 아래는 그 논의를 반영한 구현 준비 방향이며, 런타임 적용이 완료됐다는 뜻은 아니다. 세부 기술 기준은 [영문 명세 18절](../skill-supply-execution-preparation.en.md#18-owner-follow-up-interface-first-change-and-bounded-verification)이다.

> **기존 기능을 스킬 방식으로 다시 만드는 것이 아니라, 기존 기능을 그대로 사용할 수 있는 스킬 연결 규격을 만든다.**

### 선택적으로 지식을 보강한다

```text
외부 스킬 → 공급원 어댑터 → 공통 스킬 지식
                                  ↓ 필요할 때만 제공
사용자 요청 → 기존 실행 AI → 기존 도구 → 기존 서비스 → 관찰 결과
```

스킬은 브라우저·설정 호출을 대신 중계하는 새 실행기가 아니다. 스킬 지원이 꺼져 있으면 기존 실행에 스킬 검색·로더·마켓·추가 모델 호출이 필수 의존성으로 남지 않아야 한다. 켜져 있어도 호환 스킬이 없다는 이유로 원래 사용 가능했던 브라우저·설정·파일·일정 기능을 막지 않는다. 업데이트 때문에 사용자가 다시 로그인하거나 가족 비서·모델 연결을 재설정하게 해서는 안 된다.

공급원 장애나 스킬 오류는 지식 공급 경계에서 처리한다. 다만 실제 계정 권한 회수나 이미 실행된 변경의 불확실성을 무시하는 우회는 금지한다. 철회된 스킬이 이미 맥락에 들어갔다면 해당 맥락을 중단하거나 재구성하되, 원래 허용된 사용자 목표·실행 이력·현재 권한을 유지한다. 기존 경로로 돌아간다는 이유로 상품을 다시 담거나 사용자에게 같은 요청을 다시 시키지 않는다.

스킬 사용을 끄는 복구 수단은 로그인·설정·기억·Work 기록을 보존해야 한다. 이미 담긴 상품까지 되돌리는 보장은 아니다. 같은 계정에서 구버전·신버전이 동시에 장바구니 변경을 수행하는 비교 방식은 쓰지 않는다.

### 패턴은 필요한 경계에만 적용한다

| 패턴·원칙 | 적용할 곳 | 하지 않을 일 |
| --- | --- | --- |
| Ports & Adapters | 스킬 공급 인터페이스와 기존 행동 인터페이스 분리 | 전체 저장소 재설계, 박스마다 새 서비스 만들기 |
| Adapter / Anti-Corruption Layer | 외부 형식·도구 의미를 명시적으로 연결 | 이름만 비슷한 도구를 억지로 매핑, 매 호출 번역 AI 추가 |
| Design by Contract | 전제·결과·부작용·오류·재시도·상태 소유자 명시 | JSON 모양이 같으면 호환된다고 판단 |
| Branch by Abstraction | 기존 실행기를 유지한 선택적 보강과 단계적 전환 | 실행기 두 벌, 일괄 교체, 변경 작업 이중 실행 |

Design by Contract는 설계 원칙이다. 스킬 문서를 곧바로 실행 가능한 Strategy 객체로 취급하거나 사이트별 상속 구조를 만들 필요는 없다. #960 안에서 짧은 결정 기록 하나와 계약표 하나로 어떤 기존 심벌에 적용하고 무엇을 바꾸지 않을지 정한다. 새 패턴 연구 프로젝트나 이슈를 추가하지 않는다.

### 함수 모양보다 행동의 약속을 고정한다

스킬 읽기는 지정 버전의 지침·자료만 반환한다. 읽는 것만으로 브라우저 시작·설정 변경·훅 실행·계정 변경이 일어나면 안 된다. 지식을 추가해도 사용자 요청·계정·수량·현재 실행 경로 정책·독립적으로 허용된 도구는 보존한다.

실제 도구는 인수의 의미, 세션·권한 소유자, 부작용, 관찰 결과, 오류·재개 의미를 유지한다. 기존 호출자가 새 스킬 ID를 반드시 만들어야 하는 식의 변경은 피한다. 전송 성공·버튼 클릭은 목표 성공과 다르며, 방법을 바꿔도 이미 발생했을 수 있는 변경 이력을 지우지 않는다.

공급원을 추가하면 원칙적으로 공급원 어댑터가, 사이트를 추가하면 콘텐츠·연결 정보와 관련 사례가 바뀌어야 한다. 공통 실행 의미를 바꿔야 한다면 별도 변경 이유와 영향을 밝힌다. 스킬 지식 로딩에도 맥락과 정상적인 도구 왕복 비용은 생길 수 있으므로 토큰이 전혀 늘지 않는다고 약속하지 않는다. 추가 계획·전문가·검증 모델을 매번 강제하지 않는 것이 목표다.

### 검증은 변경한 경계에 맞춘다

| 변경 | 기본 확인 범위 |
| --- | --- |
| 문서·결정 기록 | 변경 내용·링크·일관성·차이와 필수 CI; 실제 모델 호출 없음 |
| 공급원·형식 어댑터 | 가짜 전송을 통한 파싱·리소스·호환성 계약 |
| 스킬 지침·사이트 힌트 | 콘텐츠 연결과 영향받는 대표 동작; 품질 확인에 필요한 소수 실모델 사례만 별도 승인 |
| 공통 실행·권한·직렬화·재개 | 관련 계약 회귀와 실제 연결부 테스트; 바뀐 위험에 맞춰 범위·독립 검토 확대 |

기존 테스트와 이미 확보된 성공 기록을 먼저 활용한다. 성공 기록은 당시 코드·모델·환경·관찰과 연결하고, 단순히 읽어 본 main 커밋을 실사용 성공 기준선이라고 부르지 않는다. 없는 기록을 채우겠다고 대규모 실사용 검증을 자동 시작하지 않는다. 기존 기능 보존은 #961부터의 조건이며, 확인된 회귀를 남긴 채 해당 경로를 기본 활성화하지 않는다.

각 구현 PR에는 바꾼 경계, 재사용할 테스트·근거, 실제 누락 위험, 추가로 확인할 최소 사례를 적는다. 기존 근거는 관련 코드·콘텐츠·연결이 여전히 적용 가능할 때만 재사용하고 현재 커밋의 필수 CI는 유지한다. 모든 공급원·모델·사이트 조합, 중복 judge, 통과할 때까지 자동 재실행, 같은 커밋의 반복 리뷰를 기본값으로 삼지 않는다.

실제 모델·계정 실행은 기본적으로 하지 않는다. 필요할 때는 경로·사례·호출 수·토큰 또는 비용·시간 상한·중단 조건·허용 행동과 정리 방법을 먼저 정한다. 불확실한 결과가 나왔다고 예산을 자동으로 늘리지 않는다. 필요한 보안·권한 검토와 필수 검사를 비용 절감 명목으로 생략하지도 않는다.

모델 없는 테스트도 AI가 테스트를 작성·고치고 전체 로그를 반복해서 읽는 비용은 있다. 기존 연결부 테스트를 재사용하고 수정은 모아서 안정된 커밋에서 확인한다. 성공 시에는 요약, 실패 시에는 해당 구간만 읽는다. #964는 하위 이슈의 적용 가능한 근거를 모으고 구체적인 누락만 확인한다.

인터페이스가 유지돼도 새로운 지침 때문에 모델의 상품 선택은 달라질 수 있다. 구조적 호환성과 모델 품질을 구분하며, 계약 테스트만으로 실제 이마트 성공률이나 절감량을 보장하지 않는다. 이번 수정은 문서·기존 이슈에만 반영하며 구현·배포·실사용 검증을 시작하지 않는다.

## 14. #960 결정 요약 (2026-10-02)

영문 기준 문서: [SKILL-PREP-01 결정 기록](../skill-prep-01-interface-decision.en.md). 런타임 동작, 의존성, 헌법 문구, 현재 목표는 바꾸지 않았다.

- **구조:** 스킬은 기존 AgentPackage에 실리는 선택적 지식이다. 새 실행기나 권한이 아니다. 읽기 전용 도구 두 개(스킬 본문 읽기, 리소스 읽기)를 기존 `DEFINITIONS`에 더하면, API와 Codex·Claude Code 브리지가 모두 같은 경로로 받는다. 스킬을 끄면 지금과 똑같은 도구 목록이 유지된다.
- **채택·적응·자체 구현:** 형식은 Agent Skills 표준을 그대로 채택한다. YAML 파싱은 PyYAML `SafeLoader`를 채택한다(#961에서 의존성 검토). Microsoft `SkillsProvider`의 경로 제한·심볼릭 링크 거부 규칙은 그대로 따르되, 자체 에이전트 루프와 승인 계층을 끌고 오기 때문에 의존성으로 쓰지는 않는다. `skills-ref`는 스스로 운영용이 아니라고 밝혀 기준 규칙으로만 쓴다. skills.sh와 Hermes는 출처 표기·격리 설치 관례만 가져온다.
- **첫 외부 공급원:** `anthropics/skills`를 정확한 커밋으로 고정해 쓰되, 각 스킬 폴더의 라이선스가 Apache-2.0인 것만 받는다. docx/pdf/pptx/xlsx는 오픈소스가 아니라 제외한다.
- **실험 결과(모델 호출 없음):** AgentOS용으로 만들지 않은 `internal-comms` 스킬을 고정 커밋에서 받아 해시가 모두 일치했고, 스크립트·훅·새 브라우저 없이 표현됐다. 경로 탈출, 심볼릭 링크, 과대 파일, 중복 키, 위험한 YAML 태그는 거부됐다.
- **남은 위험:** Codex 작업자가 소유자 `CODEX_HOME`의 기존 스킬을 스스로 찾아 쓸 수 있다. #961에서 모델 없이 확인하고 막거나 한계로 기록한다. 엄격 격리 프로필은 #961에서 스킬을 지원하지 않는다고 명시한다.
- **C16:** 사이트 노하우를 스킬 패키지에 담으려면 C16 문구 개정이 필요하다. 개정안은 결정 기록 8절에 있고, 별도 승인·독립 검토를 거쳐야 적용된다.
